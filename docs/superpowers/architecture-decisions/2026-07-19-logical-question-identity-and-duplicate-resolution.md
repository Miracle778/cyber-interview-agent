# 逻辑题目身份与重复版本处理

## 决策

题目库以“逻辑题目”计数和浏览，不再把每次 Agent 生成的候选版本都当成一道新题。候选版本仍被保留用于审计、来源追踪和重新整理。

逻辑题目的归组优先级如下：

1. 候选题显式关联的 `duplicate_of_question_id`；
2. 已发布题目的稳定 `question_id`；
3. 规范化后的题干完全一致；
4. 仅有语义相似但题干不一致时，不自动合并，继续由整理流程提示人工判断。

当新候选题命中已发布题目时，来源证据自动挂到已发布的逻辑题目上；候选版本本身不删除。未决重复版本不能直接发布，发布边界会重新检查，避免两个会话并发生成后产生重复的已发布题。

## 方案比较

- 每个候选都作为独立题目：实现简单，但目录计数失真、搜索结果充斥重复项，来源关系也被割裂。
- 自动覆盖已发布题：界面干净，但会丢失版本和审计信息，也可能把包含新知识点的答案静默覆盖。
- 逻辑题目 + 候选版本（采用）：默认只展示一个逻辑题目，保留版本；安全的来源合并自动完成，有内容差异的版本仍可查看和重新整理。

## 边界

当前的确定性归组只自动处理显式重复关系和规范化题干完全一致。模糊语义合并继续使用结构化建议，不允许 LLM 直接覆盖或删除题目。后续若增加“合并答案”“保留为独立题”等决议，应记录幂等决议回执并继续复用同一逻辑题目身份。

## 补充决策：唯一 active 版本与版本晋升

同一道逻辑题目在 `review_question_catalog` 中始终只有一个 active 指针。候选版本、历史发布文件和历史复习快照可以有多个，但都不能成为第二个同时有效的入库题目。

“更新入库版”采用版本晋升而不是新建题目：

1. 用户从同题候选版本显式发起更新；
2. 服务端验证候选与目标逻辑题相似，并把候选绑定到目标 `question_id`；
3. 记录操作开始时的 active content hash；
4. 发布前和 Catalog 投影事务内再次校验该 hash，避免并发更新覆盖；
5. Catalog 原子地指向新 draft/publication，旧 publication 和 Vault 文件保留为历史证据；
6. 已创建复习轮次继续消费自己的冻结快照，新轮次只读取新的 active 版本。

候选的 `published` 表示它曾成功发布，`is_active_version` 才表示它是否是当前复习使用的版本。界面必须分别显示“当前入库版”和“历史入库版”，不能仅凭 `published` 推断 active。
