# ADR：复盘逐题分析的有界上下文、重试所有权与失败隔离

- 状态：Accepted
- 决定日期：2026-08-03
- 适用范围：面试复盘逐题分析，不适用于转写 Cleanup 或问题提取 Map
- 关联设计：`../plans/2026-08-02-interview-retrospective-segmented-question-extraction.md`
- 关联决定：`2026-07-22-resumable-agent-task-boundary.md`

## 背景

一次真实复盘分析在问题提取成功后，于第一道题的逐题分析阶段失败。Trace 显示：

- 单题请求约 20,982 Bytes；
- 请求重复携带冻结上下文中的完整画像 Claim 与岗位文档，即使它们和当前题无关；
- Provider 抛出 `APITimeoutError`，单次用户可见等待约 91,434ms；
- 逐题 Agent 没有显式调用策略，约 30 秒的 Provider 超时被 SDK 默认重试两次，形成约三倍等待；
- 单题异常直接结束整轮分析，已提取的问题和其他可独立分析的题目没有继续推进；
- 页面“重试失败步骤”创建新重试运行，存在重放已完成工作的风险。

因此，故障不是“超时时间不够”这一项参数问题，而是四个边界同时失效：上下文没有预算、SDK 与应用重复拥有重试、故障粒度大于工作项、恢复入口没有复用原运行成果。

## 目标

- 单题模型输入不随完整画像、简历或岗位资料总量线性增长；
- 当前回答证据是分析事实主来源，画像只作为有界补充证据；
- 一次 Provider 调用的超时与重试次数可解释、可观测；
- 某一道题瞬时失败时，其他独立题目仍能完成并持久化；
- 用户恢复失败任务时不重新提取问题，也不重算已完成题目；
- 最终报告不在缺少逐题结果时伪装成完整成功。

## 候选方案与 Tradeoff

### 方案 A：只把请求超时从 30 秒调到 120 秒

否决为完整方案。更长超时可以容纳正常的慢响应，但不会减少重复上下文，也不会消除 SDK 隐式重试。若 Provider 仍失败，最坏等待会从约 90 秒扩大到数分钟；整轮故障传播和重复计算依然存在。

120 秒最终仍被保留为单次调用的外部安全上限，但它不是正确性方案，也不等价于允许无限等待。

### 方案 B：每道题继续发送完整冻结上下文

否决。完整快照有利于避免遗漏背景，但每道题都重复传输全部画像和岗位正文，延迟、Token 与隐私暴露会随用户资料增长；无关履历还可能诱导模型把面试中没有出现的经历写进判断。

冻结快照适合作为可重现的证据仓，不适合作为每次模型调用的直接 Prompt。

### 方案 C：单题失败后重新运行整轮分析

否决。问题提取、其他逐题分析和候选生成都是可持久化 Work Item。整轮重跑浪费模型调用，并可能让同一输入产生不同问题集合或不同分析结果，削弱审计与恢复语义。

### 方案 D：所有题目无限并发，并依赖 Provider 重试

否决。它可以降低理想情况下的总耗时，但会放大限流、网络抖动和本地状态竞争。首版保持确定性调度和应用层预算；未来只有在真实 Provider 数据证明需要时，才增加有界逐题并发。

### 方案 E：立即建设通用向量检索/RAG 上下文服务

暂不采用。当前只有复盘逐题分析需要从冻结画像中选择少量补充事实；引入嵌入、索引生命周期与召回评估会扩大实现面。首版使用确定性词项相关度和硬预算，保留替换为语义检索的接口边界。

### 方案 F：有界上下文视图 + 显式调用策略 + Work Item 级隔离

采用。完整冻结快照继续保证同一 AnalysisRun 可重现，但进入单题 Prompt 前先投影为有界视图；SDK 不拥有隐式重试，应用层按题控制尝试预算；恢复同一 AnalysisRun，并为新尝试创建新的 Execution。

## 决定

### 1. 冻结快照是证据仓，单题 Prompt 是有界视图

每道题始终发送：

- 当前 `question`；
- 问题与回答对应的有界转写证据段；
- 求职目标基本信息：`id / companyName / roleName / seniority`。

画像补充证据根据题目和证据段做相关性筛选：

- 最多 6 条 Claim；
- 单条序列化后最多 2,400 字符；
- 总计最多 8,000 字符；
- 只保留 Claim 身份、类型、支持状态与值；
- 岗位完整文档和无关画像不进入请求。

当前实现使用可测试的词项相关度。它不承担事实主来源，只减少明显无关信息；逐题判断仍必须锚定面试转写证据。

### 2. 一个 Provider 调用只有一个重试所有者

逐题 Agent 显式配置：

```text
max_output_tokens = 4096
request_timeout_seconds = 120
max_retries = 0
```

`max_retries=0` 关闭 SDK 隐式重试。应用层只对 `provider_timeout / network_error / rate_limited / provider_server_error` 等瞬时错误自动重试当前题，每题最多尝试 2 次。Schema、证据越界或其他确定性错误不做盲重试。

这里的 120 秒只是单次调用上限；真正的有界性来自“输入预算 + 无隐藏重试 + 每题尝试预算”。

### 3. 失败隔离在 Question Analysis Work Item

单题失败后：

1. 当前 Work Item 标记为 `retryable` 并保存稳定错误码；
2. 调度器优先继续其他尚未分析的问题；
3. 瞬时错误在本次运行预算内只重试当前题；
4. 预算耗尽后保留该题失败和其他题的 completed 结果；
5. `gap_verification / candidate_generation / final_projection` 在全部逐题结果完成前保持 pending。

最终运行可以因为仍有失败题而标记 `failed`，但不能提前丢弃其他独立工作，也不能在结果缺失时生成表面完整的报告。

### 4. 恢复同一 AnalysisRun，不重放已完成工作

页面“重试失败步骤”调用 `resumeAnalysis`：

- AnalysisRun ID 不变；
- 为恢复动作创建新的 Execution，保留每次尝试的 Trace；
- completed 的问题提取窗口、Reduce 结果和逐题分析不变；
- 只 claim `retryable / pending / interrupted` Work Item；
- 失败题成功后再执行后续汇总。

这延续了“领域长任务、Execution 尝试、Work Item 恢复断点”三层语义。

## 结果

正向结果：

- 单题输入有稳定上界，不随完整画像和岗位资料增长；
- 减少无关个人资料发送给 Provider，隐私边界更清晰；
- Trace 中一次 `model.request` 对应一次真实 Provider 尝试，不再被 SDK 隐式重试折叠；
- 一道题超时不会阻止其他题目完成；
- 用户恢复失败任务时复用已有成果，减少延迟、Token 和结果漂移；
- 汇总仍遵守完整性门禁，不把部分结果冒充完整报告。

代价与风险：

- 词项相关度可能漏掉同义表达的画像 Claim；因此画像只能作为补充，不能替代转写证据；
- 相关画像仍会发送给 Provider，不等于本地私有分析；页面与隐私说明必须保持一致；
- 每题两次、每次最多 120 秒意味着单个持续故障题仍可能占用较长时间，但等待有明确上限且不会触发隐藏的第三次调用；
- 当前逐题分析保持保守调度，总题数很多时总耗时可能偏长；并发优化需要以后基于限流和延迟数据决定；
- 同一 AnalysisRun 可以关联多次 Execution，运行中心和诊断页面必须区分“领域任务”与“本次尝试”。

## 适用边界

该模式适用于“一个长任务包含多个可独立模型工作项，并且每个工作项只需要全量上下文中的小部分证据”的 Agent 流程，例如逐题分析、逐条候选核验和分段质量检查。

不适用于：

- 问题提取：它只允许读取 confirmed transcript，禁止引入画像和岗位资料；
- 转写 Cleanup：它使用目标窗口与只读邻接上下文，恢复策略是窗口级；
- 必须全局比较全部事实的最终 Reduce：此类节点需要专门的压缩中间产物，而不是逐项检索视图。

## 重新评估条件

- 相关画像漏召回开始影响逐题分析质量；
- 画像 Claim 超过当前词项检索可稳定处理的规模；
- 多语言、同义词或缩写使词项匹配明显失效；
- Provider 延迟与限流数据支持安全引入有界并发；
- 第三个领域需要相同的“冻结证据仓 → 调用视图”能力，届时再评估抽象通用 Context Selector；
- Provider 提供可证明幂等、可恢复并且返回独立尝试 Trace 的原生批处理能力。

## 面试讲述口径

这次 Tradeoff 不是“30 秒还是 120 秒”，而是谁拥有上下文预算、重试和恢复语义。旧方案把完整快照塞进每一道题，让 SDK 和应用同时重试，并把单题失败扩大成整轮失败；资料越多，问题越严重。

最终我保留全量冻结快照用于可重现和审计，但每次模型调用只读取与当前题相关的有界证据；关闭 SDK 隐式重试，由持久 Work Item 调度器按题控制两次尝试；失败后继续其他题，恢复时复用同一 AnalysisRun 的 completed 结果。代价是需要维护证据筛选与更细的状态机，也可能漏掉同义画像信息；收益是输入规模可控、隐私暴露更小、调用次数可解释、故障可以局部恢复。
