# ADR：Agent 质量评估以业务结果为中心，并区分历史复检与真实回归

- 状态：Accepted
- 决定日期：2026-07-31
- 适用范围：全部业务 Agent、系统模型组件、Eval Pack、质量实验室与后续自动门禁
- 关联设计：`../specs/2026-07-31-agent-evaluation-v2-design.md`
- 修订关系：细化并修正 `2026-07-29-agent-trace-ledger-and-evaluation-boundaries.md` 中的质量评估与回归边界；Trace Ledger 决策保持不变

## 背景

质量实验室 v1 已具备冻结 Execution、运行 Judge、记录人工反馈、保存回归案例和比较历史评估结果的基础能力。逐项审计后确认，它仍有三项成熟度边界：

1. 当前“确定性规则”只检查所需 Trace 事件是否存在，尚未验证来源、状态机、幂等、权限等业务不变量；`blocking` 声明也未接入业务门禁。
2. 当前 Judge 直接读取较完整的冻结 Trace，并为所有维度输出 0–100 分，不能表达“不适用”或“证据不足”，也可能把基础设施缺失误判为内容质量问题。
3. 当前“回归运行”会对原 Execution 再次评估，但不会让候选 Prompt、模型、Tool 或业务 Agent 重新执行，因此属于历史结果复检，不足以证明改版有效。

如果继续把这些能力描述为“确定性门禁”和“真实回归”，会让产品承诺超过代码事实，也会让不同 Agent 的评估维度被错误复用。

## 决定

### 1. 评估对象是最终业务结果

评估的主对象不是原始模型回复，而是一次 Execution 形成的业务结果包：

```text
业务输入与来源
→ 模型原始响应
→ 规范化结果
→ 最终持久化结果与领域状态
→ 跳过 / 去重 / 降级 / 失败原因
→ 用户确认、修改或拒绝
```

Trace 用于解释结果如何形成，不能代替领域表、版本、Receipt 或最终用户决定。

### 2. Rule、Judge 与人工判断职责分离

- **确定性 Rule**：验证结构、引用、版本、状态流转、幂等、Workspace、Tool/写入权限等可由代码判定的不变量。
- **LLM Judge**：判断语义质量、表达质量、建议合理性和事实是否得到输入支持；结论必须给出证据与置信度。
- **人工判断**：处理业务偏好、模糊关系、高风险分歧和最终产品决策。

只有已经过真实案例验证的确定性业务规则才可以成为门禁。Judge 不能自动发布、删除、改写画像或改变业务 Execution 状态。

v1 现有规则在界面和文档中改称“评估证据完整性检查”，不得称为业务质量门禁。

### 3. 评估结论不用统一百分制

每个维度必须先判断适用性：

- `applicable`：证据足够且维度适用；
- `not_applicable`：该次任务没有产生需要判断的对象；
- `insufficient_evidence`：本应评估，但证据不足。

适用维度使用有锚点的等级：`meets / usable / needs_review / severe`。质量等级、问题严重度和 Judge 置信度分开保存；不再向用户展示跨 Pack 的综合 0–100 分，也不对 N/A 强行计分。

### 4. Eval Pack 按业务目标拆分

采用“公共 Runtime 不变量 + 单一业务目标 Pack”：

- `question-curation` 与 `question-revision` 分离；
- `review-round`、`review-single` 与 `review-discussion` 分离；
- `profile-ingest`、`profile-assessment`、`profile-assistant` 与 `profile-write-boundary` 分离；
- `job-requirement-analysis` 独立；
- `project-deep-dive-coaching` 与 `project-question-generation` 分离。

同一领域内的不同 Graph 不再因为共享页面或数据表而强制复用同一组维度。

### 5. 来源、推断与模型补全必须可区分

题目、画像、岗位要求和项目事实统一保留来源语义：

- 直接来源；
- 规范化表达；
- 模型推断或补全；
- 用户本人补充或确认；
- 不受支持；
- 冲突作为独立关系记录。

用户确认模型补全内容，只会把它变成“用户确认”，不会倒推成“原材料直接支持”。题目答案至少分别保存 `sourceAnswer` 与 `supplementalAnswer`，再派生展示用 `referenceAnswer`。

### 6. Judge 只接收任务所需的最小评估视图

Evaluation v2 从业务结果包生成 task-specific `EvaluationView`，默认不把完整私有 Trace 发送给外部 Judge。Secret 永不进入 Trace 或 Judge；敏感个人信息、普通画像事实和公开材料采用不同披露级别。

完整私有 Trace 只允许在用户明确授权的高级诊断场景读取。评估记录必须显示 Judge Provider、模型和数据范围。

### 7. 历史复检与真实回归是两种产品能力

v1 现有能力正式命名为“重新质检历史结果”：

```text
同一历史业务结果
→ 更换或重跑 Eval Pack / Judge
→ 检查评估标准或 Judge 结论是否变化
```

真实回归必须重新运行候选业务 Agent：

```text
冻结真实输入、必要领域状态与预期不变量
→ 在隔离 Evaluation Runtime 中运行基线版本和候选版本
→ 执行确定性业务规则
→ 对两份业务结果做盲测 pairwise Judge
→ 必要时人工确认
```

案例需记录 Graph、Prompt、模型、推理强度、Tool、Schema、上下文装配、业务代码、Eval Pack 和 Judge 版本。基础设施失败与内容质量失败分别统计。普通案例默认运行一次；高风险案例可运行三次观察波动。

### 8. v1 历史不可重写

- v1 Pack、结果、人工反馈和回归案例继续只读可查；
- 页面标记为“初版质检 / 历史结果复检”；
- v2 使用新 Pack ID、版本和结果契约，不把 v1 分数迁移成 v2 等级；
- v1 与 v2 不做跨版本趋势比较；
- 数据库只做增量迁移，不删除现有用户数据。

## 关键维度边界

- 材料处理完整性、状态推进、幂等、来源定位、Workspace 与写入权限属于确定性规则。
- 题目来源忠实度只评估“声称来自原文”的部分；明确标记的模型补全由“补全质量与透明度”判断，不能因原文没有答案直接判低。
- 题目覆盖率只有在明确题目清单等可靠分母存在时才计算；随手笔记只评估处理完整性、候选完整性和潜在遗漏，不伪造精确百分比。
- 相似度算法只负责召回疑似重复项；Judge 分类关系，用户决定合并、保留或建立父子关系。
- 画像字段按字段级来源判断；资料没有记录某项经历，只能判“未记录/未评估”，不能推断用户没有该经历。
- JD 先做段落分类，团队背景不进入岗位门槛；显式要求与系统推断的准备建议分开。
- 项目深挖的价值由“是否减少真实信息缺口”衡量，不以问题听起来难不难为准；通用建议不能写成用户项目事实。

## 结果

正向结果：

- README、产品界面和代码能力保持一致；
- 不同 Agent 获得符合自身业务目标的评估口径；
- Judge 偏差、证据缺失和 N/A 不再被一个总分掩盖；
- 后续可以真正比较 Agent 改版，而不是重复给历史结果打分；
- 私有简历、JD 和对话不会默认完整发送给第二个模型。

代价：

- 需要为每个业务目标维护 Outcome Adapter、Eval Pack 和真实案例；
- v1 与 v2 在一段时间内并存；
- 真实回归比历史复检消耗更多模型调用与隔离运行资源；
- 可阻断规则必须先积累标注案例和误报证据，不能快速铺开。

## 不变量

1. 评估失败不改变原业务结果。
2. Judge 不拥有领域写 Tool。
3. Trace 不成为业务真相。
4. 证据不足不能伪装成低分或高分。
5. 不适用维度不参与汇总。
6. 用户确认不改变内容的来源类型。
7. v1 历史结果不可重写为 v2。
8. 没有重新运行候选业务 Agent，就不能声称完成真实回归。
9. 只有经过案例验证的确定性业务规则才可阻断。
10. 外部 Judge 默认只获得最小任务视图。

## 重新评估条件

- Judge 与人工在代表性样本上达到稳定一致率；
- 某项确定性规则准备从提示升级为阻断；
- 引入远程、多用户或集中式评估服务；
- 需要将回归门禁接入 CI/CD；
- Provider 支持更稳定的随机种子或原生评估接口。
