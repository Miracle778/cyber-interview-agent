# 面试复盘 Cleanup 的稳定原文单元与有界结构化输出

日期：2026-08-02

状态：Superseded

由 `2026-08-02-clean-transcript-artifact-and-internal-window-boundary.md` 取代。本文仅保留旧 SourceUnit/Turn/Diff 方案的 Tradeoff 历史。

## 背景

真实的一小时面试转写验证暴露了两个相互放大的问题：

- 每个约 4,000 字符窗口同时返回整理后全文和 40～60 条完整修订记录，成功响应已经消耗 7,356～8,159 个输出 Token，稍复杂的窗口会触及应用配置的 8,192 Token 上限；
- Cleanup Agent 直接生成绝对字符 offset 和 `originalText`。即使结构化 JSON 完整，真实样本中的修订位置仍无法与不可变原文精确对应。

输出达到上限时，Anthropic-compatible Provider 以 `stop_reason=max_tokens` 停止生成。兼容层把未完成的 Tool JSON 包装为 `raw_arguments`，随后被 `CleanupOutput(extra="forbid")` 拒绝。通用 `ToolStrategy(handle_errors=True)` 又把残缺输出和错误追加到上下文继续调用，形成高 Token 的结构化纠错循环；应用层仍会原样重试相同窗口。

这不是单一 Provider 的偶发格式错误，而是模型职责过重、结构化输出过大和重试所有权不清共同造成的系统性失败。

## 决定

### 1. 程序拥有原文切分、稳定 ID 和绝对位置

后端先把不可变 SourceVersion 按自然边界切成完整原文单元。每个单元携带稳定 `unitId`、`sourceStart`、`sourceEnd` 和原文。模型只引用 `unitId`，不得生成或修改绝对 offset。

窗口只由完整原文单元组成，重叠也按单元表达。Reducer 以 `unitId` 和后端 offset 为权威，不再相信模型计算的字符位置。

### 2. 模型返回精简的单元级对话轮次

Cleanup Agent 每个单元返回 `unitId` 和有序 `turns`。每个 turn 包含说话人角色、显示名、置信度、修订稿和必要的不确定原因。

单元只有一个说话轮次时不重复返回原文，程序把整个 Source Unit 作为该轮次证据。只有单元内部确实包含说话人切换时，模型才为各 turn 返回精确 `sourceText`；程序要求这些片段顺序拼接后与单元原文完全一致，并据此计算轮次 offset。

模型仍不返回绝对 offset、Segment ordinal 和逐条修订的完整审计元数据。多轮次场景增加的 `sourceText` 是局部边界证明，不是自由生成的证据副本；验证失败时只重试或拆分当前窗口。

### 3. 程序通过 Diff 生成 CorrectionRecord

后端用原文单元和 `correctedText` 做确定性字符 Diff，生成精确的原文范围、`originalText` 与 `suggestedText`。纯插入与相邻字符合并为非空替换范围，以兼容当前证据模型。

格式与安全术语匹配可由确定性规则标为低风险；数字、否定和时间等可确定识别的关键语义变化升级为高风险。审核页面直接展示模型 `correctedText`，但普通大幅措辞、语序或无法由允许术语唯一确认的变化会升级为整段高风险待确认，不能直接进入确认版本。模型不返回风险等级，因此不能降低程序判定的高风险。

字符 Diff 是定位机制，不等于用户任务。只有“安全可采用”或“关键且必须决定”的变化才物化为 CorrectionRecord；被程序否决的自由改写仍可在 Trace 中诊断，但不能把一小时转写膨胀成上千条待办。

### 4. 一个模型调用只允许一次结构化尝试

Cleanup Agent 关闭 `ToolStrategy` 内部自动纠错。Provider 的一次响应要么形成合法单元结果，要么失败返回给持久工作项调度器。网络重试、结构化修复和业务重试不得在不同层无界叠加。

### 5. 截断和无效结构触发拆小，不原样重跑

`stop_reason=max_tokens` 稳定分类为输出截断。超时、输出截断、缺失/重复 `unitId` 和无法形成完整单元结果时，只拆分当前失败窗口；已经完成的窗口保持不可变。

残缺 `raw_arguments` 不能容错补括号或作为部分结果落盘，因为它没有完整性和证据边界保证。

## 备选方案与 Tradeoff

### 只把上限从 8,192 调到 16K 或 32K

否决为主方案。它可以暂时降低截断率，但修订数量会随输入内容增长，无法建立稳定上界；模型 offset 仍然不可靠，成本和延迟也同步扩大。提高上限只能作为额外余量，不能承担正确性。

### 只把窗口从 4,000 字符缩小

否决为完整方案。缩小窗口能降低输出体积，但仍要求模型重复原文、生成 offset 和大量 Correction 元数据；窗口变多后调用次数、重叠去重和说话人连续性成本增加。拆小应作为恢复手段，不能代替协议瘦身。

### 容错解析 `raw_arguments`

否决。真实 Trace 中的 `raw_arguments` 是被 Token 上限截断的无效 JSON，不是完整 JSON 的双重编码。补括号或部分解析会把缺失尾部的结果误当正式证据。

### 继续让模型返回精确 offset，再做模糊匹配

否决。模糊匹配可能在重复短语中锚定错误位置，也会把模型的计数错误转化成不可解释的后端猜测。稳定 ID 和程序 Diff 能直接消除这类不确定性。

### 为每条修订单独调用模型

否决。输出虽小，但调用数量、延迟和费用不可控，且会失去窗口上下文。单元级修订稿一次返回、程序批量 Diff 是更平衡的边界。

## 结果

正向结果：

- 结构化输出大小接近修订稿正文，不再随审计字段倍增；
- 普通单轮次单元不重复原文；只有发生说话人切换的少量单元增加原文片段，因此不会恢复为每条修订重复原文的无界协议；
- offset、原文引用和重叠去重由确定性代码保证；
- 截断、Schema 错误和业务校验失败具有独立错误类型与恢复动作；
- 每次 Provider 调用可观测且有界，不再产生纠错风暴；
- 现有 SourceVersion、CleanupVersion、CorrectionRecord 和用户确认页面继续复用。

代价：

- 需要维护自然单元切分、Diff 合并和风险分类规则；
- 模型返回的是单元修订稿，后端必须防止大比例重写和漏返单元；
- 多轮次恢复依赖模型逐字复制局部原文片段；复制或覆盖错误会使当前窗口进入有界重试，换取的是不依赖模型字符计数的轮次边界；
- 窗口与重叠从字符范围演进为完整单元范围，现有测试和 Reducer 需要迁移；
- 确定性风险规则应保持保守，部分本可自动接受的修订会进入人工确认。
- 模型整理稿在审核阶段保持可见；无法唯一确认的大幅改写会增加少量整段核对项，但避免页面正文与 Provider 响应出现两套互相矛盾的内容。

## 适用边界

该模式适用于必须保留证据位置、输出可能接近输入规模、且结果需要人工审核的长文本 Agent。纯摘要、自由创作或不需要原文锚点的任务不必引入 Source Unit 与 Diff 成本。

## 面试讲述口径

这个案例的核心 Tradeoff 不是“把 Token 调大还是把文本切小”，而是决定哪一层拥有不可逆的事实。模型适合做依赖上下文的错字和说话人判断，但不适合同时承担字符计数、证据定位和无限增长的审计输出；程序适合持有不可变原文、稳定 ID、Diff 和风险门禁，却不能独立完成语义纠错。

最终选择是把协议从“模型返回完整领域对象”收窄为“模型返回有界语义建议，程序物化领域证据”。代价是增加切分、Diff 与保守风险规则，收益是输出规模可估算、offset 可证明、失败可局部恢复、审计链不依赖模型自报。若面试官追问为什么不只加 Token，可以用真实数据回答：成功窗口已经达到 8,159 输出 Token，而 offset 即使在完整响应中仍全部校验失败，所以容量和正确性必须分别解决。
