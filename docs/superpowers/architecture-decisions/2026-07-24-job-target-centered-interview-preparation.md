# ADR：以求职目标组织个人资料与项目深挖训练

- 状态：Accepted
- 决定日期：2026-07-24
- 适用阶段：R3 可信个人资料收口、R4 求职目标与项目深挖、R5 面试复盘、R6 模拟面试
- 关联设计：
  - `docs/superpowers/specs/2026-07-10-product-development-roadmap-design.md`
  - `docs/superpowers/specs/2026-07-20-r3-personal-profile-agent-design.md`
- 决策来源：用户通过一轮逐项产品追问确认

## 背景

R3 已实现简历上传、版本、Evidence、Claim 审核、评估、受约束修改和简历助手，但“用户为什么要长期维护这些资料”没有形成明确的产品回报。继续按原计划建设 Claim 级知识发布、撤销和发布范围页面，可以完成技术闭环，却仍可能让产品停留在复杂的简历管理器。

用户确认希望同时获得三类价值：

- 长期维护的可信个人档案；
- 针对目标岗位的可解释差距分析；
- 基于真实项目经历的个性化面试训练。

三者不能作为并列入口。个人档案是底座，目标岗位提供判断参照，训练才是用户获得提升的主要过程。

## 选择标准

- 产品主价值必须直接服务面试准备，而不是资料管理本身；
- 岗位差距必须可追溯到 JD 要求和已确认的个人事实，不能依赖不可解释的单一百分比；
- 训练必须产生可复用的长期产物，而不是只留下聊天记录和一次性评分；
- Agent 不能把模型总结、用户临时表达或估算自动写成个人事实；
- 个人资料、岗位要求、训练状态、题库和项目讲解资产必须有清晰的状态所有者；
- 核心流程不能被“发布到知识库”这一技术性操作阻塞；
- 第一条纵向切片应复用现有简历、题库、复习和统一 Agent Runtime，避免同时建设完整模拟面试和求职管理平台。

## 候选方案

### 方案 A：以简历管理和润色为中心

用户上传、比较和优化简历，Agent 主要提供评估与改写。

优点：流程短，市场认知成熟。

拒绝原因：与通用简历优化产品差异有限；现有 Evidence、Claim、跨 Agent 查询和题库能力明显过重；无法解释用户为何要持续维护结构化资料。

### 方案 B：以个人画像和知识发布为中心

用户确认个人资料后选择发布到 Active Knowledge，后续 Agent 统一从知识库检索。

优点：技术边界统一，知识库拥有显式发布与撤销流程。

拒绝原因：把内部存储边界变成核心用户流程；用户需要重复经历“确认事实—选择范围—批准发布”才能开始岗位分析；资料是否进入通用知识库与某个求职目标能否读取已确认事实不是同一个授权问题。

### 方案 C：以求职目标为业务中心，以项目深挖为第一训练闭环

个人资料保存可信事实；求职目标保存岗位要求和准备状态；训练围绕目标岗位深挖真实项目，并沉淀项目讲解卡和分类缺口。

优点：资料维护、岗位分析和训练形成因果链；直接复用 R2 题库/复习与 R3 个人资料；每次训练都能更新可见的准备状态。

代价：需要重定尚未开发的 R3.4，并为 R4 设计新的岗位要求、映射、讲解卡和缺口领域模型。

## 决定

采用方案 C，并规定以下边界。

### 1. 产品承诺与目标用户

第一阶段面向有 2～8 年经验、拥有真实项目经历、正在准备跳槽的软件工程师。

产品承诺是：

> 针对用户想去的岗位，基于其真实做过的事情，找出准备差距，通过连续项目深挖训练帮助用户把经历讲清楚、讲具体并经得住追问。

个人资料管理不是最终价值；它负责保证后续分析和训练不编造用户经历。

### 2. 业务组织中心

求职目标是岗位分析、项目训练、题库任务、复盘和模拟面试的一级聚合对象。目标可以只有岗位方向，也可以绑定一个或多个具体 JD；没有完整 JD 时允许使用用户确认的岗位方向要求模板。

个人简历和已确认画像是可被多个求职目标复用的长期资产，不复制进每个目标。简历页面继续负责材料、版本、事实确认和资料修正，不承担无目标的泛化训练。

### 3. 岗位分析表达

岗位分析以逐项要求清单为核心：

```text
岗位要求
→ 已有可靠证据
→ 部分匹配或待深挖
→ 资料不足
→ 确实缺少经历
```

每项结论必须关联 JD 原文、已确认 Profile Claim、项目讲解卡或明确的未知状态。产品可以展示“已覆盖/待验证/资料不足”的计数，但不把单一匹配百分比作为核心结论。

### 4. 第一训练场景与长期产物

R4 第一条端到端切片只实现项目深挖：

```text
创建求职目标
→ 填写岗位方向或 JD
→ Agent 提取要求，用户确认
→ 要求与已确认经历逐项关联
→ 用户选择一个核心项目
→ Agent 连续追问
→ 生成项目讲解卡和分类缺口
→ 更新岗位准备状态
```

项目讲解卡至少包含：

- 项目背景；
- 个人职责；
- 关键方案及选择理由；
- 最难的问题与解决过程；
- 结果和可量化影响；
- 取舍、失败与复盘；
- 与当前目标岗位相关的专项追问及准备状态。

通用项目事实属于个人资料域；某个 JD 下的适配结论、高风险问题和准备状态属于求职目标域。删除求职目标不删除已经确认的通用项目讲解事实。

### 5. 新事实和缺口处理

训练中产生的新事实不能直接更新 Profile Claim 或项目讲解卡。Agent 只能创建带来源对话和精确 Diff 的待确认补充，用户确认后由确定性领域服务写入。

“回答不好”必须区分：

| 缺口类型 | 状态所有者 | 后续动作 |
|---|---|---|
| 资料缺口 | Profile | 创建待确认补充 |
| 表达缺口 | Project Narrative / Training | 继续追问并完善讲解卡 |
| 知识缺口 | Question / Review | 生成候选复习题，进入现有确认与复习流程 |
| 经历缺口 | Job Target | 明确记录，不允许 Agent 编造经历 |

缺口分类可以由 Agent 建议，但任何会改变长期个人事实或正式题库的结果都继续经过用户确认。

### 6. 已确认资料的消费边界

岗位分析和训练不依赖 Profile 发布到 Active Knowledge。用户创建求职目标并选择当前简历后，目标域可以通过 application service 直接读取同一 Workspace 中有界的已确认 Profile Claim。

读取规则：

- 只返回当前 confirmed Claim Version；
- 排除 pending、rejected、superseded 和未获准的敏感字段；
- 默认返回结构化事实和 Evidence ID，不返回完整原始简历；
- 原文只通过已有受限 Tool 按需读取；
- Workspace、目标、Session、Execution、Tool scope 继续由服务端注入和校验；
- 调用外部模型时，页面需要明确说明将使用选中的岗位和个人资料。

通用知识发布可以作为未来的跨模块检索、导出或共享能力，但不是 R4–R6 使用个人资料的前置条件。

### 7. 当前简历助手的边界

简历助手保留为资料维护助手，只负责解释识别结果、定位来源、发现冲突、整理经历和生成待确认修改。岗位差距、项目深挖和模拟面试进入求职目标工作区，避免一个开放聊天窗口同时承担所有职责。

### 8. 准备状态

每个求职目标的核心进度由可行动事实组成：

- 岗位要求中已有证据、待验证和资料不足的数量；
- 核心项目讲解卡的完成情况；
- 尚未解决的高风险追问；
- 已进入题库和尚未完成的技术复习项。

聊天次数、文件数量和模型综合评分不作为主要进度指标。

## R3–R6 路线影响

- R3：收口为可信个人资料底座和受控 confirmed-profile 查询；暂停原知识发布闭环，不再建设发布范围主页面。
- R4：改为求职目标、JD 要求确认、经历映射、单项目深挖、项目讲解卡、分类缺口和准备状态的第一纵向闭环。
- R5：真实面试复盘继续挂在求职目标下；新增项目事实进入待确认补充，知识缺口进入题库。
- R6：完整模拟面试消费求职目标、项目讲解卡、高风险问题和复习薄弱点，不重新复制个人资料。

## 结果

正向结果：

- 当前简历能力获得明确下游用途；
- 岗位分析、题库和训练不再是彼此孤立的页面；
- 用户每次训练都能得到可复用资产和可见进度；
- Profile 的证据与确认边界继续成立；
- 无需为了内部检索强迫用户理解知识发布。

负向结果与风险：

- 已创建但尚未使用的 Profile PublicationSelection/Publication schema 暂时成为预留扩展点；
- 需要调整已确认的 R3 spec、plan 和浏览器验收清单；
- R4 比单纯岗位 CRUD 更复杂，必须按一条纵向切片实施，不能并行铺开完整模拟面试、申请追踪和 Todo；
- 项目讲解卡的通用事实与目标专项准备状态必须分开，否则会重新产生跨目标污染。

## 第一切片非目标

- 单一匹配百分比；
- 自动修改个人资料或编造经历；
- 完整技术面/HR 面模拟；
- 招聘网站同步、自动投递和申请进度自动化；
- 强制把个人资料发布到知识库；
- 同时覆盖所有职业和无真实项目经验的用户；
- 自由 ReAct 写入、通用 Time Travel 或无限 Planner。

## 重新评估条件

满足任一条件时重新评估：

- 产品出现多个本地或外部模块需要脱离求职目标检索个人资料，且直接 Profile 查询造成重复授权逻辑；
- 用户确实需要导出、共享或跨 Workspace 使用个人画像；
- 大量用户没有真实项目经历，需要为应届生或转行者设计不同的训练主线；
- 岗位要求映射无法通过关键词和结构化模型稳定解释，需要引入新的检索或语义索引；
- 项目讲解卡在多个目标间频繁产生冲突，需要把通用事实和目标适配内容拆成更细的独立聚合。
