# 阶段 Learning 掌握包模板

每个主要产品切片在 `docs/learning/<stage>/` 创建七份本地文件。材料必须基于最终代码、真实验证和实际故障；禁止用通用教程、虚构故障或单个 README 代替。文档深度按风险分类，不以总行数或字数作为质量门槛。

## 先选择学习档案

在写七件套前，根据主要学习难点选择一个档案：

- `foundation`：共享 Runtime、安全、middleware、持久化、可观测等基础能力；
- `stateful`：显式状态机、人工决策、幂等副作用或重启恢复；
- `integration`：多个既有子系统、真实 Provider 或前后端契约的纵向闭环；
- `experience`：主要改变信息架构、交互、可访问性和响应式行为，且不新增高风险后端状态机。

同时命中多个档案时选择风险更高的档案，不得为了缩短材料降级分类。`overview.md` 使用固定声明：

```markdown
## 学习档案

- 类型：`foundation`
- 风险驱动：
  - 第一项阶段特有风险；
  - 第二项阶段特有风险。
```

风险驱动必须描述本阶段的真实状态、信任、一致性、外部协议或交互风险，不能写“代码复杂”“需要学习”之类通用理由。

## `overview.md`

必须包含：

- `## 学习基线`：最终提交或明确代码版本、前置知识；
- `## 学习档案`：固定类型声明和至少两个阶段风险驱动；
- `## <阶段> 解决的问题`：用户问题、工程问题和阶段边界；
- `## 如何使用本掌握包`：推荐阅读与实践顺序；
- `## 当前边界`：尚未覆盖和后续演进；
- `## 掌握标准`：能够 Explain、Trace、Review、Debug 或实现什么。

## `architecture.md`

必须包含以下五个二级章节：

- `## 总体结构`：与最终代码一致的图或结构化流程；
- `## 组件职责`：每个组件负责什么以及明确不负责什么；
- `## 状态所有权`：数据库、文件、Graph state、前端缓存和外部系统分别拥有什么事实；
- `## 信任与一致性边界`：身份、权限、secret、并发、幂等、fail-open；体验档案聚焦 UI 真相源、查询一致性与可访问性；
- `## 关键设计取舍`：采用方案、被放弃方案和选择理由。

图和文件清单不能代替状态与边界分析。

## `code-walkthrough.md`

`foundation`、`stateful`、`integration` 至少包含两条以 `## 链路` 开头的真实链路；`experience` 至少一条。每条链路都要：

1. 从真实 API、页面事件、生命周期或 Graph 节点开始；
2. 标出关键函数/组件和输入输出；
3. 经过状态、持久化或查询缓存边界；
4. 到达用户可见结果；
5. 解释至少一个关键失败或恢复分支。

代码路径和符号使用反引号；只列文件名不算链路。

## `failure-journal.md`

每个二级章节只记录真实故障，并能明确回答：现象、错误假设或为什么难发现、根因、修正、验证证据、提前发现方式。推荐使用这些标签，便于机器与人工复核：

```markdown
## 故障标题

- 现象：……
- 错误假设：……
- 根因：……
- 修正：……
- 验证证据：……
- 提前发现：……
```

没有真实故障时，明确写“本阶段无真实故障”并引用对应 verification，不能虚构案例。

## `interview-questions.md`

使用三级标题写问题并给出可追问答案。`foundation`、`stateful`、`integration` 至少五题；`experience` 至少三题。整体覆盖设计理由、状态/数据边界、失败路径、安全或一致性和验证证据。

## `presentation-script.md`

必须包含：

- `## 3 分钟版本`：问题、核心方案、关键取舍、结果和边界；
- `## 10 分钟讲解提纲`：架构、代码链路、状态/信任边界、故障、验证和后续演进。

不能只复述功能列表。

## `exercises.md`

必须包含：

- `## 主练习`：至少覆盖 Explain、Trace、Review、Debug 或小型实现中的两类，并说明所有权证据位置；
- `## 降级形式`：时间不足时的代码审阅、故障定位、流程图或伪代码；
- `## 练习状态`：未开始、进行中、已完成和证据位置。

练习不阻塞产品开发、提交、合并或下一阶段。未完成练习记录为理解债务，不记为产品缺陷。

## 生成节奏

1. 阶段开始只确定档案和风险驱动，不生成完整七件套。
2. 最终实现、针对性测试和浏览器验收稳定后生成一次。
3. 最终回归后只刷新代码路径、测试数字和真实故障证据。
4. 运行一次机器门禁，再与上一个同档案阶段做一次人工抽查。

## 阶段关闭检查

1. 七份文件基于最终代码，无未完成占位符。
2. 档案与风险匹配，没有为了减少篇幅降级。
3. 状态所有权、真实链路和失败边界足以支持对应掌握标准。
4. failure journal 只包含真实故障或明确的无故障记录。
5. 对照上一同档案阶段，内容深度没有明显退化，也没有重复灌水。
6. 运行 `scripts/check_stage_docs.py`，并在 verification 与最终汇报记录一次人工抽查结果。
