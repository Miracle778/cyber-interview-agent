# R3 统一个人画像产品纠偏规格

日期：2026-07-24

状态：Accepted

适用阶段：R3 可信个人资料底座

优先级：本规格是 `2026-07-20-r3-personal-profile-agent-design.md` 的产品模型补充；如两者在用户入口、画像来源或页面职责上冲突，以本规格为准。

## 1. 问题定义

当前 R3 已经实现简历上传、不可变版本、Evidence、Claim 候选、用户确认、只读 Agent Tool、受控修改计划和 confirmed-profile 查询。但是页面仍以简历文件、原文片段和待确认 Claim 为主，用户看不到一份能回答“我是谁、擅长什么、做过什么、取得过什么结果”的个人画像。

页码、行号和原文片段只能解决来源追溯，不能构成个人画像。继续优化片段标题会改善解析器可见性，但不会解决产品主对象缺失的问题。

本次纠偏把 R3 的用户主对象从“被解析的简历”改为“统一个人画像”。简历继续是重要来源，但不再是画像本身或使用前置条件。

## 2. 产品定义

个人画像是一份岗位无关、由用户确认、可长期维护的个人能力档案。

它包含：

- 事实层：技能、工作经历、项目经历、教育、认证、成果；
- 关系层：项目与工作/教育的关联、技能与实际使用经历的关联；
- 归纳层：职业概况、能力方向和代表性亮点；
- 来源层：简历提取、本人补充、对话补充和系统归纳；
- 完善层：明确缺少的时间、职责、结果和量化信息。

个人画像不包含：

- 针对某个岗位的匹配度、差距或准备度评分；
- 项目技术取舍、失败复盘和面试追问；
- 自动生成且未经确认的长期事实；
- 一份由模型自由改写、无法追溯的个人介绍。

岗位匹配和针对性表达属于 R4 求职目标；项目深挖属于后续项目训练。

## 3. 核心用户路径

```text
上传简历或从空白画像开始
→ 生成画像草稿
→ 用户逐项确认、编辑或拒绝
→ 形成统一个人画像
→ 用户继续手动补充或通过画像助手补充
→ 新来源只产生增量建议和冲突
→ 已确认画像供后续岗位分析和训练受控读取
```

用户不需要先上传简历。没有简历时，可以直接创建技能、经历和项目，也可以通过画像助手逐步补充。

## 4. 统一画像与多来源

### 4.1 单一画像

同一 Workspace 只有一份统一个人画像。多份简历是不同来源或表达版本，不分别创建画像。

同一事实可以由多份来源支持。针对岗位生成简历时，从统一画像选择相关内容，而不是让某一份简历重新定义用户。

### 4.2 来源类型

每个画像版本必须记录一种来源：

| 来源 | 含义 | 是否直接确认 |
|---|---|---|
| `resume_extraction` | 从简历 Evidence 提取 | 否 |
| `user_input` | 用户在画像编辑器主动保存 | 是 |
| `conversation` | 从画像助手对话整理 | 否 |
| `agent_inference` | 系统根据已确认事实归纳 | 否 |

`user_input` 不强制伪造 Evidence，但必须保存创建者、时间和版本。其他三类来源必须保留可解释的输入引用；简历提取引用 Evidence，对话补充引用消息，系统归纳引用已确认画像版本。

### 4.3 正式画像与草稿

- 已确认画像是正式内容，可以提供给画像助手和下游消费者；
- 待确认建议可以在画像页面预览，但不能进入普通 Agent 回答或 confirmed-profile；
- 用户在画像编辑器主动填写并点击保存，视为显式确认；
- 简历提取、对话整理和系统归纳始终先生成建议；
- 每确认一项就增量更新画像，不要求全部确认后一次生成。

## 5. 画像结构

### 5.1 稳定栏目

画像使用固定骨架，AI 负责归纳和表达，不自由创建事实栏目：

1. 职业概况；
2. 能力方向；
3. 代表性亮点；
4. 工作经历；
5. 项目经历；
6. 核心技能；
7. 教育经历；
8. 认证与成果；
9. 待完善信息。

### 5.2 事实类型

内部稳定事实类型扩展为：

```text
skill
project
experience
education
certification
achievement
link
```

职业概况、能力方向和代表性亮点是画像展示内容，必须引用已确认事实。它们可以由用户直接维护，也可以由 Agent 生成待确认建议。

内部仍使用同一套 Claim/ClaimVersion 版本机制保存三种展示内容：

```text
summary
direction
highlight
```

它们不是新的事实来源，也不会绕过确认；这样可以保留编辑历史、来源和支持关系。

### 5.3 项目边界

项目画像保存：

- 名称、时间和背景；
- 用户角色与职责；
- 关键工作；
- 技术栈；
- 结果与可量化成果。

项目深挖阶段再处理：

- 方案选择原因；
- 替代方案和权衡；
- 最难问题；
- 失败与复盘；
- 面试讲解与追问。

项目作为独立对象，可选关联工作经历或教育经历。关联不复制项目内容。

### 5.4 技能表达

技能不由 AI 自动标注“精通、熟练”。画像展示技能与实际项目、工作经历的使用关系，例如“在 3 个项目中使用”。用户主动填写的自评可以保留，并明确标记为本人评价。

### 5.5 归纳内容

职业概况、能力方向和代表性亮点不能随事实变化静默覆盖：

```text
已确认事实变化
→ 归纳内容标记可能过期
→ 系统生成修改建议
→ 用户查看 Diff
→ 接受、编辑或忽略
```

用户亲自编辑过的归纳内容优先级高于 AI 建议。

## 6. 关系与版本

### 6.1 画像关系

第一里程碑支持：

```text
project -> experience    belongs_to
project -> education     belongs_to
skill   -> project       used_in
skill   -> experience    used_in
highlight -> claim       supported_by
```

关系本身需要 Workspace 归属校验，不允许跨 Workspace 引用。

### 6.2 卡片级版本

- 每条技能、经历、项目、教育、认证、成果和归纳内容保留版本；
- 用户可以查看历史版本并恢复；
- 恢复创建新的确认版本，不改写历史；
- 不建设整个画像任意时间点回滚；
- 不回滚简历文件、Agent 会话或其他领域资产。

### 6.3 新版简历

导入新版简历只生成新增、修改、删除提醒和冲突建议：

- 不清空已确认画像；
- 不覆盖本人补充；
- 新版中未找到旧事实时，提示用户决定是否保留；
- 多个来源支持同一事实时合并来源关系，不复制事实。

## 7. 来源删除

删除简历前必须显示受影响的画像信息。

用户逐项选择：

- 删除相关画像信息；
- 保留画像信息，并将来源状态改为“原简历已删除，由本人保留确认”；
- 取消删除。

如果画像信息还有其他有效来源，删除一份简历不会使其失去支持。系统归纳内容失去全部事实依据时进入待核对状态。

## 8. 页面信息架构

一级入口改为：

| 页面 | 主要任务 |
|---|---|
| 我的画像 | 阅读、完善和维护已确认画像 |
| 待确认 | 处理简历、对话和系统归纳产生的建议 |
| 简历与来源 | 上传、版本、原文、来源、归档和删除 |
| 画像助手 | 查询画像、追问缺失信息、生成待确认更新 |

默认进入“我的画像”。

### 8.1 我的画像

页面优先级：

1. 画像概况、多个能力方向和可选主要方向；
2. 3–5 条用户确认并排序的代表性亮点；
3. 工作时间线与关联项目；
4. 项目卡片；
5. 技能与实际使用关系；
6. 教育、认证和成果；
7. 明确的待完善信息；
8. 来源与版本入口。

默认是阅读模式。用户按卡片编辑，不使用整页长表单或字段级后台表格。

主行动根据状态变化：

- 无画像：上传简历或从空白开始；
- 有待确认：确认新信息；
- 有缺失：补充具体字段；
- 已可用：使用画像助手或进入求职目标。

不展示抽象画像总分。“待完善”必须是可行动事实，例如“项目缺少量化结果”。

### 8.2 待确认

按来源和类型分组，使用用户语言：

- 来自简历的新信息；
- 根据经历归纳出的能力；
- 对话中整理出的补充；
- 可能与现有画像冲突的内容。

支持逐项接受、编辑后接受、拒绝和显式批量选择。页面不展示 Claim、Evidence、snake_case 或内部 ID。

### 8.3 简历与来源

保留现有不可变版本、解析状态、失败恢复、原文定位、归档和删除。

页码、行号和原文仅在“查看依据”后出现。画像首页只显示“来自简历 v2”“本人补充”“系统归纳”等轻量来源标记。

### 8.4 画像助手

画像助手承担：

- 基于已确认画像回答；
- 发现缺失并追问；
- 把对话补充整理为待确认建议；
- 解释某条待确认建议及其依据。

普通回答只使用已确认画像。只有用户正在审核具体建议时，助手可以读取该建议和来源，并明确称其为待确认内容。

调用外部模型时采用：

- 默认最小范围；
- 持续显示当前使用的画像类别；
- 用户可以展开查看和取消具体画像卡片；
- 敏感字段默认排除，首次使用需单独授权；
- Event、Audit 和模型日志不保存完整个人原文。

## 9. 领域边界

继续复用现有 `profile_claims/profile_claim_versions` 作为稳定画像事实和版本底座，不建立第二套画像真相。

需要新增：

- Workspace 级统一画像展示设置；
- Claim 来源类型与来源引用；
- Claim 关系；
- 代表性亮点排序；
- 用户直接创建/编辑/恢复服务；
- 统一画像读取投影；
- 对话补充和系统归纳 Proposal 来源。

`profile_action_plans` 继续处理 Agent 生成的多项修改。用户主动编辑单张卡片不需要再经过 Action Plan，但仍需要乐观锁、幂等键和版本回执。

## 10. 数据重置边界

当前本地个人资料测试数据尚未进入正式使用，可以在新模型稳定后清除并重新测试。

只允许清理目标 Workspace 的：

- 个人材料、版本、Evidence；
- Profile Claim、版本、Proposal、关系和展示设置；
- Profile Assessment、Action Plan、画像会话和相关 Execution/Event；
- 对应私有材料文件。

不得清理：

- Workspace 配置；
- Provider 与模型绑定；
- 题库、候选题和整理会话；
- 复习轮次与历史；
- Knowledge 和其他领域数据。

数据库迁移本身不能静默删除用户数据。当前 Workspace 重置通过显式、目标可验证的本地命令执行。

## 11. 验收标准

1. 清空当前 Workspace 的个人资料测试数据；
2. 上传简历后生成结构化画像草稿，而不是以原文片段充当画像；
3. 确认技能、经历和项目后，“我的画像”立即形成可读内容；
4. 用户可以手动新增简历中没有的项目或成果；
5. 首页能回答“我是谁、擅长什么、做过什么、取得了什么结果”；
6. 原文、页码和版本只在点击“查看依据”后出现；
7. 普通画像助手回答只使用已确认内容；
8. 对话补充生成待确认建议，确认后画像更新；
9. 新版简历只产生增量建议，不覆盖已有画像；
10. 页面展示明确待完善项，不展示虚构总分；
11. 删除来源时逐项处理受影响画像；
12. 390/768/1024/1440 下四个入口和核心任务均可达。

## 12. 成熟度边界

本次完成后，R3 成为可维护、可追溯、可供下游受控读取的统一个人画像产品。

仍不包含：

- 岗位匹配和岗位准备度；
- 针对岗位的亮点排序和自我介绍；
- 项目技术取舍和面试深挖；
- OCR、外部账号同步和多用户共享；
- 通用 Time Travel 或 Agent 自由写工具。
