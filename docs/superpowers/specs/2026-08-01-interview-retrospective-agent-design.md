## 1. 问题与产品目标

用户完成真实面试后，通常只有手机录音转出的文字、聊天式转写或事后回忆。逐条整理面试官问题、核对自己的回答、识别缺口并再分别维护题库和项目资料，成本很高，也容易在下一轮准备前遗忘。

本阶段提供一条完整闭环：

```text
选择求职目标
→ 导入转写或事后回忆
→ 整理说话人与问题
→ 用户确认整理结果
→ 后台渐进分析逐题表现
→ 审核推断问题、缺口与改进回答
→ 确认题目、项目经验和画像候选
→ 进入复习或发布复盘总结
→ 围绕报告继续对话并版本化修正
```

产品承诺是：

> 把一轮真实面试变成有来源、可修正、可行动的复盘记录，并把用户确认的知识缺口和真实经历安全地送回既有准备闭环。

价值来自可追溯的问题与回答、明确的不确定性、逐题可执行改进和受控的资产沉淀，不来自聊天次数、笼统总分或无法解释的综合评价。

## 2. 目标用户与适用边界

首版面向：

- 已有明确岗位方向或具体求职目标的软件工程师；
- 能从手机录音工具导出文字，或愿意在面试后手工记录重点；
- 希望同时复盘技术、项目、系统设计、行为与 HR 问题；
- 希望将确认后的知识缺口加入题库，并补充真实项目事实。

首版不专门覆盖：

- 音频、视频的上传与自动转写；
- PDF、Word、图片或 OCR 输入；
- 联网搜索和外部事实核验；
- 自动隐私脱敏；
- 完整求职申请进度管理；
- 全局 Todo、日历、提醒或截止时间；
- 模拟面试执行；
- 多用户协作。

## 3. 领域所有权

### 3.1 求职目标是必需父级

每场面试复盘必须属于一个 `JobTarget`。用户可以：

- 选择已有求职目标；
- 在新建复盘时仅填写岗位名称，快速创建无 JD 的轻量求职目标；
- 稍后补充公司、职级和 JD。

临时输入可以停留在客户端草稿，但开始持久化处理前必须绑定求职目标。删除求职目标会删除其复盘记录，但不会删除已确认进入全局题库、统一画像、通用项目讲解或 Knowledge 的资产。

### 3.2 一轮面试对应一场复盘

同一公司的技术一面、二面、主管面和 HR 面分别保存。求职目标聚合多轮时间线、重复缺口和未完成行动项，但不把多轮文本合并为一条问题时间线。

### 3.3 复盘领域拥有的资源

面试复盘领域拥有：

- 面试元数据与生命周期；
- 原始输入版本；
- 说话人整理版本和片段；
- 原始问题、推断问题及用户决定；
- 分析运行、逐题结果、整场汇总和四类缺口；
- 改进提纲与参考回答草稿；
- 复盘内行动项；
- 题目、画像、项目经验和总结的待审核候选；
- 复盘持续对话的 Session 引用；
- 发布与跨领域写入 Receipt。

面试复盘领域不拥有：

- 求职目标、JD 和岗位要求；
- 统一画像 Claim 和 Evidence；
- 全局项目与已确认项目讲解；
- 正式题库和复习掌握度；
- Knowledge 文档；
- Provider、模型配置和 Agent Trace。

## 4. 输入与版本

### 4.1 两种输入类型

用户必须选择：

- `transcript`：录音工具导出的转写，尽量保留原始对话；
- `recollection`：用户事后回忆，默认可能缺少面试官原话和完整顺序。

首版支持直接粘贴以及 `.txt`、`.md` 文件。单个源版本正文最多 500,000 个 Unicode 字符；空白输入、二进制内容和超限输入稳定失败，不创建半成品分析。

后续补充创建新的源版本，不能静默修改旧正文。源版本记录内容哈希、类型、创建时间和来源文件名；文件名仅用于展示，不参与本地路径解析。

录音转写还必须冻结覆盖范围：`full_dialogue` 表示基本包含双方对话，`candidate_only` 表示主要只有候选人讲话，`mixed_unknown` 表示混合或无法判断。事后回忆固定使用 `mixed_unknown`。覆盖范围属于源版本证据，整理或分析运行中不能随界面状态改变。

### 4.2 原文、整理结果与分析结果分离

```text
SourceVersion (immutable raw text)
  → CleanupVersion (speaker/segment organization)
  → AnalysisRun + AnalysisVersion (question results and summary)
```

- 原文永远按用户提交版本保存，不被整理步骤覆盖；
- 整理版本引用一个明确源版本；
- 分析运行引用一个已确认整理版本，以及冻结的岗位、画像和题库上下文摘要；
- 新版本完成前，旧的 active 分析结果继续可读；
- 同一输入与同一上下文的重复请求通过 input digest 和 idempotency receipt 去重。

### 4.3 单独清除原始文本

用户可以清除原始文本并保留结构化复盘：

- 清除源正文以及逐题结果中保存的原文摘录；
- 保留正文哈希、版本元数据、结构化结论、用户确认决定和下游 Receipt；
- 清除后不能重新整理、重新分析或查看来源原句；
- 页面持续显示“原始记录已由用户清除”；
- 既有正式题库、画像、项目讲解和 Knowledge 资产不受影响。

## 5. 说话人整理与确认关口

### 5.1 整理输出

本地确定性预处理先统一换行、空白和显式说话人标签，再由结构化 Cleanup Agent 输出：

- 有序片段；
- `candidate / interviewer / unknown` 说话人角色；
- 规范化显示名，如“我”“面试官 A”“面试官 B”；
- 源文本 offset；
- 置信度；
- 疑似串行、缺失或无关标记。

模型不能修改源正文，只能生成新整理版本。处理长文本时按有重叠的有界窗口读取，Reducer 按源 offset 单线程合并，禁止并行 Worker 直接写最终顺序。

一小时以上的转写按以下长文本契约执行：

- 本地预处理优先在换行、句末和显式说话人边界切分；硬上限为 4,000 字符，相邻窗口保留 400 字符上下文；
- 最早未完成窗口先单独处理，首个成功结果冻结最多 8 个原始标签到角色/显示名提示；后续窗口最多并发 2 个；
- 重叠区只作为上下文。每个窗口携带 `emitFrom`，模型不得输出该 offset 之前的片段，最终 Reducer 仍按绝对 offset 单线程写正式顺序；
- Cleanup Provider 调用显式使用 120 秒超时并关闭 SDK 隐式重试；每个持久工作项最多尝试 2 次；
- 大于 2,500 字符的超时窗口原子替换为两个更小且有重叠的持久窗口，只重跑失败范围；一个窗口失败不阻止其他窗口完成和保存；
- 停止、刷新、进程重启和用户重试均只领取未完成窗口，已完成输出不可删除或重复调用；
- 连接测试只证明 1 Token `ping` 可达，不等同于真实长文本结构化任务验收。真实 Provider 验收使用不含个人信息的中长合成转写，并单独记录耗时、失败窗口和恢复结果。

### 5.2 用户确认

正式分析前必须确认整理版本：

- 高置信度片段正常显示；
- 不确定说话人、缺失内容和疑似错位片段重点提示；
- 支持交换全部说话人、修改单段角色、重命名面试官和忽略无关片段；
- 不要求用户逐句确认；
- 确认后整理版本冻结；
- 修改已确认整理结果创建新版本。

首版不增加自动脱敏或独立隐私预检。页面沿用 Provider 调用提示，说明已确认转写与所选上下文将发送给用户配置的模型。

## 6. 问题还原与确认

### 6.1 问题单元

每道问题形成一个 `QuestionUnit`：

- 问题文本；
- 类型；
- 原始或推断来源；
- 问题片段和回答片段引用；
- 时间线顺序；
- 推断依据和置信度；
- `pending / confirmed / rejected / superseded` 决定状态。

问题类型为：

- `technical_knowledge`；
- `project_experience`；
- `system_design`；
- `behavioral_collaboration`；
- `motivation_hr`；
- `unknown`。

### 6.2 原始问题与推断问题

- 转写中明确出现的面试官问题标记为“原始问题”；
- 根据候选人回答倒推的问题标记为“推断问题”；
- 推断问题必须展示依据片段、置信度和不确定标识；
- 用户可以确认、编辑或删除推断问题；
- 未确认推断问题可以获得临时分析草稿；
- 未确认推断问题不能形成正式整场结论、题库候选或岗位风险；
- 修改问题或回答绑定后，只重算受影响问题和整场聚合。

## 7. 渐进分析

### 7.1 后台运行

分析使用现有 Session、Execution、Checkpoint、Trace 和取消语义，不建设第二套 Runtime。公开阶段为：

```text
整理问题
→ 分析逐题表现
→ 验证缺口
→ 生成候选与行动项
→ 完成
```

页面显示：

- 当前阶段；
- 已完成问题数 / 总问题数；
- 当前处理问题；
- 累计耗时；
- 已保存结果数；
- 失败位置和可恢复动作。

用户可以离开、刷新、停止和重试。停止不领取新工作项，当前持久化临界区完成后安全停止；已完成逐题结果保留。重试复用同一运行或创建明确 retry execution，不重复生成候选。

### 7.2 渐进展示

- 问题整理完成后立即显示问题列表；
- 每道题分析完成后逐条出现；
- 尚未完成的题显示等待状态；
- 中途停止时明确标记报告不完整；
- 整场汇总、跨题重复缺口和候选去重只在逐题阶段结束后生成。

### 7.3 一小时级转写的问题提取

- 问题提取只读取已确认、未忽略的完整段落，不再截取前 60,000 字；
- 按最多约 12,000 字的完整段落窗口执行，相邻窗口重叠 4 个段落，最多并发 2 个窗口；
- 每窗结果以 `question_extraction:<firstOrdinal>:<lastOrdinal>` 独立持久化，超时窗口可原子拆分，已完成窗口不重跑；
- 窗口之间只传递重叠的原始 Segment 和结构化覆盖范围，不传递自然语言摘要；
- 原话问题锚定首个问题段落，推断问题锚定首个回答段落；相同文字但锚点不同仍是两次独立出现；
- 重叠窗口中同锚点结果只合并证据 ID，`continues_previous` 才能并入前一锚点；
- 只有全部窗口完成后，`question_reduce` 才确定性归并并创建正式 QuestionUnit。任一窗口耗尽重试时保留已完成窗口输出，但不发布部分正式题目。

### 7.4 分析依据

分析使用冻结的：

- 已确认整理版本；
- 当前求职目标与岗位要求；
- 已确认统一画像与项目讲解；
- 题库和 active Knowledge 中有界、脱离路径的短摘录。

首版不联网。结论区分：

- 有内部证据直接支持；
- 与个人项目事实冲突；
- 模型通用知识判断，建议核对；
- 信息不足，无法可靠判断。

模型不能把通用知识判断伪装成已核实事实。

## 8. 逐题结果与整场汇总

### 8.1 不提供总分

逐题结论枚举为：

- `strong`：表现较好；
- `improvable`：有改进空间；
- `high_risk`：明显风险；
- `insufficient_evidence`：信息不足。

每道题必须包含：

- 做得好的地方；
- 需要改进的地方；
- 关键遗漏或事实风险；
- 对应来源片段或来源不可用状态；
- 分析依据层级；
- 分析置信度；
- 四类缺口；
- 改进提纲；
- 参考回答草稿。

整场只做事实汇总，如各类问题数量、各类缺口数量、重复风险和未确认推断数，不计算综合分数。

### 8.2 四类缺口

沿用 R4：

- `material`：缺少可验证资料或事实；
- `expression`：事实存在但表达结构、重点或节奏有问题；
- `knowledge`：技术概念、原理或方案理解不足；
- `experience`：缺少真实经历，不能靠措辞或模型补造。

经历缺口只能形成岗位风险或行动项。Agent 禁止生成虚构项目事实。

### 8.3 改进回答

- 改进提纲描述推荐顺序、遗漏点和应补证据；
- 参考回答只使用原回答与已确认个人事实；
- 缺少指标或事实时使用明确占位提示；
- 草稿不自动进入画像、项目讲解或 Knowledge。

## 9. 候选与跨领域写入

分析完成后自动生成待审核候选，但不直接写正式资源。

### 9.1 题目候选

来源于知识缺口、回答不完整的问题和用户确认保留的问题。写入前：

- 与现有题库进行相似匹配；
- 展示“关联已有题、补充已有题、仍创建新题”；
- 用户确认后调用现有 Review 领域服务；
- 提供“立即练习 / 稍后练习”；
- 立即练习复用现有 Review Agent。

### 9.2 项目经验与画像候选

- 项目职责、方案、结果和取舍优先生成项目讲解候选；
- 可能成为长期个人事实的内容生成 Profile Proposal；
- 展示现有 Claim/讲解与本次新增证据；
- 用户选择关联、补充、新建或拒绝；
- 写入必须经过目标领域的 version、confirmation 和 receipt 校验。

### 9.3 去重和幂等

- 模型只给出匹配建议，不自动合并；
- 同一候选只能决定一次；
- 部分失败保留失败项和稳定错误码；
- 重试不能重复创建正式资源；
- 已拒绝或忽略的相同候选保留 fingerprint，避免反复建议。

## 10. 复盘内行动项

行动项属于当前复盘，不建设全局 Todo。字段包括：

- 标题和具体动作；
- 来源问题或缺口；
- `material / expression / knowledge / experience` 类型；
- `pending / completed / dismissed` 状态；
- 可用下游动作；
- 创建和完成时间。

求职目标可以聚合未完成数量。首版不支持截止时间、提醒、优先级排程或跨模块任务分配。

## 11. 持续对话与局部重算

每场复盘拥有一个持久可见会话。用户可以追问分析依据、要求解释、重组表达或指出事实错误。

- 解释类对话只产生消息；
- 涉及问题、回答绑定或结论变化时生成明确修正建议；
- 用户确认后创建新的整理或分析版本；
- 单题修改优先局部重算；
- 说话人或跨题边界变化重算受影响范围；
- 用户可以主动重新分析整场；
- Agent 只有有界只读 Tool，不能直接改画像、题库、项目讲解或 Knowledge。

## 12. 发布复盘总结

分析完成后始终保存结构化复盘领域记录。发布到 Knowledge 是可选动作。

新增 `interview_retrospective` 文档类型。用户逐项选择：

- 面试基本信息；
- 已确认问题；
- 选中的表现结论；
- 已确认经验总结；
- 行动项；
- 题库、岗位和项目讲解链接。

明确不发布：

- 完整原始转写；
- 未确认推断问题；
- 被拒绝候选；
- Agent 对话全文；
- Prompt、模型原始响应或运行事件。

发布通过现有 Knowledge Draft、HITL 和 Publication Receipt，重复操作不能覆盖用户外部编辑。

## 13. 生命周期、结果与删除

复盘生命周期为：

- `active`；
- `archived`；
- `recycled`。

面试结果是用户维护的可选事实：

- `pending`：等待中；
- `passed`：已通过；
- `failed`：未通过；
- `cancelled`：已取消；
- `unrecorded`：未记录。

Agent 不推断面试结果。面试日期、轮次名称和备注可以独立更新，不改写历史分析。

永久删除仅在回收站提供。删除复盘拥有的源版本、整理版本、分析、会话引用、候选和行动项；运行中的 Execution 阻止永久删除。已确认进入其他领域的正式资产继续保留，并移除或 tombstone 来源链接。

## 14. 页面与交互

### 14.1 双入口、单一数据

- 一级导航新增“面试复盘”，用于快速新建、最近复盘和跨岗位历史；
- 求职目标详情新增复盘入口和该目标下的时间线；
- 两个入口读取同一资源；
- 详情页持续展示公司、岗位、轮次和面试日期。

### 14.2 报告优先、对话辅助

桌面端详情结构：

1. 顶部：返回、目标与轮次、运行状态、归档和更多操作；
2. 摘要区：本次复盘状态、问题/缺口/行动数量和下一步；
3. 主工作区左侧：有序问题列表和处理状态；
4. 主工作区右侧：当前问题详情、来源、分析、提纲和参考回答；
5. 独立区域：候选资产、行动项和发布；
6. 可展开侧栏：继续与 Agent 讨论；
7. 高级运行详情只从运行摘要下钻，不占用业务主界面。

页面遵循既有应用布局规范：操作优先、正文不使用过宽长行、筛选控件复用共享 Select、状态卡可点击且默认数字真实、同级标签切换不隐藏其他标签。

### 14.3 响应式

- `>= 1024px`：问题列表与详情双栏；
- `768–1023px`：窄双栏或抽屉详情；
- `< 768px`：单列，问题详情、候选和对话分层进入；
- 390px 支持新建、粘贴、进度、阅读、简单候选决定和对话；
- 大段校对与并排版本比较以桌面效率为主；
- 所有断点不得横向溢出。

## 15. API 资源与错误边界

建议一级资源：

- `InterviewRetrospectiveResource`；
- `InterviewSourceVersionResource`；
- `InterviewCleanupVersionResource`；
- `InterviewQuestionUnitResource`；
- `InterviewAnalysisRunResource`；
- `InterviewQuestionAnalysisResource`；
- `InterviewAssetCandidateResource`；
- `InterviewActionItemResource`。

所有资源使用 camelCase，正文按详情端点按需返回。列表不返回原始转写或完整回答。

稳定错误码至少包括：

- `retrospective_target_required`；
- `retrospective_source_too_large`；
- `retrospective_source_cleared`；
- `retrospective_cleanup_not_confirmed`；
- `retrospective_busy`；
- `retrospective_version_conflict`；
- `retrospective_question_confirmation_required`；
- `retrospective_candidate_conflict`；
- `retrospective_delete_blocked`；
- `retrospective_model_not_configured`；
- `retrospective_analysis_failed`。

写请求必须携带 idempotency key；版本化资源使用 expected version；非 Workspace 路径全部重新校验 Workspace 所有权。

## 16. 模型角色与 Agent 边界

新增两个模型用途：

- `retrospective_analysis`：整理、问题还原、逐题分析、汇总和候选提取；
- `retrospective_chat`：复盘后的持续讨论和修正建议。

分析用途使用结构化输出、无业务写 Tool。聊天用途仅允许读取当前复盘、已授权岗位、确认画像、题库和 active Knowledge 的有界摘录。

首版禁止：

- 模型直接确认问题或候选；
- 模型直接发布 Knowledge；
- 模型创建或修改正式 Profile Claim；
- 模型绕过 Review 领域服务写题库；
- 自由文件路径、任意 SQL、任意代码执行；
- 通用 Time Travel；
- 递归委派或无限 Planner。

## 17. 运行中心与可观测性

Registry 新增业务 Agent 类型“面试复盘”，运行中心任务名使用业务语义，例如“复盘：某公司后端二面”，不得使用源文件哈希或内部 graph 名作为主标题。

业务详情只展示阶段、进度、耗时、已保存结果和失败恢复。Prompt、完整上下文、Tool 参数和 Provider 原始响应继续只在已开启高级诊断时通过 Agent Trace 查看。

Trace 写入失败 fail-open：不得导致复盘业务失败。Source、Cleanup、Analysis 和候选领域表是业务权威来源；JSONL Trace 不是复盘状态源。

## 18. 验收标准

### 18.1 输入与整理

- 可以在已有目标下创建复盘，也能以内联轻量目标开始；
- transcript 与 recollection 明确区分；
- 原文和整理版本不会互相覆盖；
- 不确定说话人可批量或逐段修正；
- 未确认整理版本不能启动正式分析；
- 500,000 字符边界和重复提交有稳定行为。

### 18.2 问题与分析

- 原始问题和推断问题视觉、字段和下游权限明确区分；
- 未确认推断问题不会进入正式候选；
- 问题列表先出现，逐题结果渐进出现；
- 停止、刷新和后端重启后保留完成工作项；
- 单题修改只重算该题及整场聚合；
- 页面不展示整场总分；
- 技术判断清楚标记内部证据、模型判断或信息不足。

### 18.3 沉淀与练习

- 分析自动生成候选，但未经确认不改正式资源；
- 相似题和相似经历提供关联、补充或新建选择；
- 确认题目后可以直接进入现有复习流程；
- 部分失败可安全重试，不重复创建题目或 Claim；
- 发布总结不包含原始转写和未确认推断。

### 18.4 生命周期与隐私

- 清除原始记录后不能重新分析，结构化报告仍可读；
- 删除复盘不删除已确认下游资产；
- 多轮复盘在目标下独立保存并聚合；
- Agent 不推断实际面试结果；
- 运行中复盘不能永久删除。

### 18.5 页面质量

- 1440、1024、768 和 390px 不横向溢出；
- 桌面端报告为主、对话为辅；
- 手机端可完成新建、查看进度、阅读和简单候选决定；
- 键盘、输入法、焦点返回、加载、空状态、失败和重试符合共享前端规范；
- 从运行中心和复盘业务页均可下钻高级运行详情并返回原上下文。

## 19. 首版完成定义

首版完成不是“模型返回了一段总结”，而是：

1. 一场真实文字记录形成可恢复的版本化复盘；
2. 用户能确认整理结果和推断问题；
3. 逐题分析有来源、有不确定性、有改进动作；
4. 知识缺口能经确认进入题库并开始复习；
5. 真实项目事实能经确认进入现有画像或讲解审核路径；
6. 复盘总结可选择性发布且不泄露完整转写；
7. 刷新、停止、失败、重试、局部修改和删除均有明确且幂等的状态语义。
