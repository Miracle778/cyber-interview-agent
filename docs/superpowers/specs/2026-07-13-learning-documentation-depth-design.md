# Learning 掌握包深度治理设计

## 1. 背景与目标

R1.2 与 R1.3 的 learning 掌握包能够支持 Explain、Trace、Review、Debug 和实践，但后续部分阶段逐渐收敛成“七个文件存在且标题齐全”。这不是单纯由阶段功能减少造成的：R1.4 的持久化 HITL、R1.6 的真实 Agent 集成和 Runtime Middleware 1.0 都包含高风险状态、恢复或跨层边界，其掌握材料却显著更薄。

本次治理同时完成两件事：

1. 补强已经交付但深度不足的掌握包，使内容与最终代码风险匹配；
2. 把后续生成规范从“统一模板 + 存在性检查”升级为“风险档案 + 结构化证据 + 人工抽查”。

目标不是让每个阶段达到相同篇幅，也不使用总字数作为质量代理。门禁应拒绝空洞或过度压缩的文档，同时允许体验型切片保持精炼。

## 2. 本次补强范围

### 2.1 深度补强

- `r1-4-hitl`：补齐 action/receipt/delivery/run 的状态关系、interrupt/resume、重启 reconciliation、幂等与信任边界。
- `r1-6`：补齐模型绑定快照、Provider secret 解析、结构化/流式调用、Runtime/HITL/发布闭环、刷新和重启恢复。
- `runtime-middleware-1-0`：补齐 pipeline/洋葱执行、usage、context budget、标题、loop guard、HITL adapter、SQLite 延迟写入、OpenTelemetry/Langfuse fail-open 和扩展方式。
- `pre-r2-experience-stabilization`：保留体验切片的紧凑程度，但补齐 source/draft 生命周期、Markdown 安全渲染、查询刷新、按需 HITL 和响应式边界。

### 2.2 新增缺失掌握包

- 新建 `settings-experience` 七件套，覆盖配置概览、分组导航、渐进披露、TanStack Query 真相源、脏表单保护、可访问性和响应式验收。

### 2.3 基准包

- R1.2、R1.3、R1.5 的正文保持不做机械扩写；增加学习档案声明，使新门禁能够按同类风险校验。
- R1.2 的额外 `notes.md` 可以保留，但七件套仍是固定交付单元。

## 3. 学习档案

每个 `overview.md` 必须在 `## 学习档案` 中按以下固定格式声明一个档案和对应风险驱动：

```markdown
## 学习档案

- 类型：`foundation`
- 风险驱动：
  - 第一项阶段特有风险；
  - 第二项阶段特有风险。
```

档案由阶段的主要学习难点决定，而不是由文件数量、提交规模或阶段编号决定。机器门禁只解析固定的类型声明和风险列表，避免从自由文本猜测分类。

### 3.1 `foundation`

用于共享 Runtime、安全边界、middleware、持久化或可观测底座。要求解释稳定契约、组件职责、状态所有权、信任/一致性边界、失败降级和扩展方式。

适用：R1.2、R1.3、Runtime Middleware 1.0。

### 3.2 `stateful`

用于包含显式状态机、人工决策、幂等副作用或重启恢复的领域切片。要求状态转换、操作键/版本、恢复路径和失败后的事实归属。

适用：R1.4、R1.5。

### 3.3 `integration`

用于把多个既有子系统接成真实纵向闭环的切片。要求跨层调用链、契约转换、真相源、刷新/恢复和外部协议边界。

适用：R1.6、Pre-R2 体验稳定化。

### 3.4 `experience`

用于主要改变信息架构、交互层级、可访问性和响应式行为，且不新增高风险后端状态机的切片。允许更短，但仍必须解释 UI 状态来源、查询失效、关键交互分支和验收证据。

适用：设置页体验重构。

如果阶段同时命中多个档案，选择风险更高、掌握要求更强的档案，不得为了缩短文档降级分类。

## 4. 七件套内容契约

### 4.1 `overview.md`

必须包含学习基线、学习档案、阶段解决的问题、使用顺序、当前边界和掌握标准。学习基线必须指向最终提交或明确的最终代码版本；学习档案必须列出至少两个阶段特有的风险驱动。

### 4.2 `architecture.md`

必须包含：

- `## 总体结构`：与最终代码一致的图或结构化流程；
- `## 组件职责`：说明各组件做什么以及不做什么；
- `## 状态所有权`：区分数据库、文件、Graph state、前端缓存和外部系统中的事实；
- `## 信任与一致性边界`：说明身份、权限、secret、并发、幂等或 fail-open 边界；体验档案可聚焦数据真相源、查询一致性和可访问性边界；
- `## 关键设计取舍`：至少说明一个采用方案、被放弃方案及理由。

图不能代替文字说明，组件清单也不能代替状态与边界分析。

### 4.3 `code-walkthrough.md`

`foundation`、`stateful` 和 `integration` 至少提供两条真实链路，`experience` 至少提供一条。每条链路必须从真实入口开始，经过关键函数/组件、状态或持久化边界，到达用户可见结果，并说明至少一个关键分支。

路径和符号使用反引号标注。只罗列文件名、不解释输入输出与状态变化，不视为完整链路。

### 4.4 `failure-journal.md`

每个故障章节只记录真实发生的问题，并明确包含：现象、错误假设或为什么难发现、根因、修正、验证证据、提前发现方式。没有真实故障时必须明确声明并引用 verification，不能虚构。

### 4.5 `interview-questions.md`

`foundation`、`stateful` 和 `integration` 至少五题，`experience` 至少三题。答案需要支持追问，整体覆盖设计理由、状态/数据边界、失败路径、安全或一致性，以及验证证据。

### 4.6 `presentation-script.md`

保留三分钟版本和十分钟提纲。两种版本都要包含问题、方案、关键取舍、结果和未覆盖边界；不能只复述功能列表。

### 4.7 `exercises.md`

主练习必须要求产生所有权证据，并至少覆盖 Explain、Trace、Review、Debug 或小型实现中的两类。保留降级形式和练习状态；用户练习继续不阻塞产品开发。

## 5. 机器门禁与人工抽查

### 5.1 机器门禁

扩展 `scripts/check_stage_docs.py`，从 `overview.md` 读取学习档案，并检查：

- 档案值合法且存在阶段风险驱动；
- architecture 五个必需章节存在；
- code walkthrough 的链路数量满足档案要求；
- interview questions 数量满足档案要求；
- failure journal 包含结构化故障证据或明确的无故障声明；
- exercises 包含证据要求、降级形式和状态；
- 原有占位符、verification 与 plan 一致性检查继续保留。

门禁不设置全局字数或行数下限。结构检查用于拦截明显退化，不能替代内容真实性判断。

### 5.2 人工抽查

阶段关闭时只做一次人工抽查，回答：

1. 架构是否能解释状态由谁拥有、失败后什么仍然是真相；
2. 代码链路能否从入口走到可见结果，而不是文件清单；
3. 故障是否真实且与 verification/commit 一致；
4. 与上一个同档案阶段相比，是否遗漏了同等风险下应解释的内容；
5. 文档是否存在重复堆砌，可以在不损失掌握目标的情况下压缩。

人工抽查记录在 verification，不增加第八份学习文档。

## 6. 测试策略

校验脚本使用单元测试覆盖：

- 高风险档案的 7 行 architecture 被拒绝；
- 非法或缺失档案被拒绝；
- 链路、问题或故障证据不足时被拒绝；
- 合格的 experience 档案可以比 foundation 更短；
- 原有 verification/plan 冲突检查不回退；
- 补强后的所有现有掌握包均通过对应门禁。

这是文档治理切片，不修改产品运行代码，不重复后端、前端或浏览器全量回归。

## 7. 执行与同步边界

- 正式设计、实施计划、模板、校验脚本和脚本测试提交到 Git。
- `docs/learning/` 与 `docs/verification/` 继续保持本地文件；分支完成和合并后必须显式同步到主仓库并逐目录核对。
- 不修改 `docs/my_idea.md`。
- 一次完成历史补强，不在后续每个产品 Task 增量重写七件套；阶段代码稳定后生成一次，最终验收后刷新证据。
- 本切片完成代表学习材料和生成规范达到新的质量基线，不代表用户已经完成学习或练习。
