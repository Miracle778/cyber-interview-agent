# 双轨开发与项目所有权工作流设计

## 1. 背景

Cyber Interview Agent 不只是一个需要交付的产品，也是用户在求职面试中展示 Agent Harness 理解、工程判断和实践能力的项目。

当前开发大量借助 Codex 和 Claude 完成。如果只持续增加功能而不保存设计脉络、故障经验和学习入口，用户会在切换会话、上下文压缩或项目规模扩大后失去对系统的可解释性。反过来，如果要求用户在每个任务完成前先独立掌握或实现代码，又会阻塞开发并浪费可用的 Agent 额度。

因此项目采用“持续开发 + 延迟吸收”的双轨模式。

## 2. 目标

工作流必须同时满足：

1. 产品开发不因用户当前学习速度而暂停。
2. 每次设计、实现、审阅和故障修正都沉淀为可复用的学习资产。
3. Codex、Claude、新会话和上下文压缩后都能恢复同一套工作方式。
4. 用户可以在面试前按目标岗位选择性清偿理解债务。
5. 项目成熟度和用户掌握度分别记录，不能互相冒充。

## 3. 不做什么

- 不要求用户逐行重写 Agent 生成的代码。
- 不把用户练习作为功能提交、合并或进入下一阶段的前置条件。
- 不为了制造学习任务而重复实现正式产品功能。
- 不把本地学习笔记混入正式产品规格和发布文档。
- 不声称用户已经掌握尚未完成所有权验收的模块。

## 4. 双轨状态

### 4.1 产品轨道

产品轨道负责：

- 需求和边界确认；
- 设计规格与实施计划；
- 代码实现和委派；
- 自动测试、代码审阅和人工验收；
- 分支提交、合并和成熟度更新。

产品轨道是否完成，只由功能和质量证据决定。

### 4.2 所有权轨道

所有权轨道负责：

- 阶段作用和架构说明；
- 关键请求链路与代码地图；
- 设计取舍和替代方案；
- 真实故障、原因和修正；
- 面试问题、讲解稿和实践练习；
- 已掌握、待掌握和待实践事项。

所有权轨道可以落后于产品轨道。落后的内容记录为“理解债务”，但不阻塞产品开发。

## 5. 跨 Agent 入口

仓库使用三个层次，避免规则漂移：

1. 根目录 `AGENTS.md`：Codex 和其他兼容 Agent 的强制入口。
2. 根目录 `CLAUDE.md`：Claude Code 的强制入口。
3. 本文档：双轨工作流的唯一权威来源。

`AGENTS.md` 和 `CLAUDE.md` 只保存启动顺序、不可违反的规则和本文档路径。详细流程只在本文档维护。

如果入口文件与本文档冲突，以本文档为准；如果产品规格与本文档冲突，产品行为由已批准的产品规格决定，协作方式仍由本文档决定。

## 6. 新会话恢复协议

任何 Agent 在开始项目工作前必须按顺序执行：

1. 先用 `git worktree list`、`git status --short` 和最近五条提交定位权威工作树；
2. 读取该工作树的精简 `task_plan.md`、`findings.md` 和 `progress.md`；
3. 读取当前阶段对应的 spec 和 implementation plan；
4. 只有需要解释或修改协作规则时才读取本文全文；
5. 只有追溯特定历史决定时才读取 `docs/superpowers/history/`。

恢复后必须先确认：

- 当前产品阶段和下一任务；
- 当前成熟度边界；
- 尚未解决的代码或验收问题；
- 当前理解债务和用户练习状态；
- 本次任务由 Codex、Claude 还是用户承担。

不得只根据聊天摘要猜测项目状态；仓库文件和实际代码是权威证据。三个根规划入口合计目标不超过 400 行，历史内容归档后不再作为启动输入。

## 7. 阶段工作流

### 7.1 开发前

- 一次性收集需要用户决定的产品或架构问题，并提供推荐项。
- 说明本阶段完成后用户能看到什么，以及明确不包含什么。
- 评估任务复杂度：高耦合、跨层和高风险任务由 Codex 实现；普通、边界清晰的任务可委派 Claude；用户练习单独安排。
- 评估执行隔离等级：简单任务直接在权威仓库工作树的新建普通分支上完成；只有复杂、高风险、长周期、并行、委派或阶段级任务才创建独立 worktree。
- 评估 skill 成本：`superpowers:*` 系列默认不调用。只有任务属于阶段/切片、跨层能力、关键状态机、安全边界、大范围重构等大颗粒复杂工作，或用户主动点名要求时，才允许选择其中与真实风险直接匹配的最小 skill 集合。普通、简单、定向任务即使涉及代码、测试或计划，也不得自动进入 superpowers/planning 流程；仓库使用 `docs/superpowers/` 目录不构成调用理由。
- 不要求用户在开发前完成系统学习。

### 7.1.1 任务复杂度分级

简单任务通常满足以下条件：

- 范围清楚，涉及少量文件；
- 不改变核心架构、状态机、安全边界或数据兼容策略；
- 不需要并行开发、跨 Agent 交接或长期上下文；
- 可以用少量定向测试验证；
- 不需要阶段级 verification、learning 或文档门禁。

简单任务可以在主仓库工作树中新建 `codex/...` 普通分支执行。若当前工作树已有无关脏改，Agent 必须保护这些改动；只有文件不重叠时继续，否则先向用户确认。

复杂任务包括：

- 阶段或切片实施计划；
- 跨后端、前端、API、数据库或浏览器验收的联动改动；
- 关键状态机、HITL、安全边界、数据重建或迁移策略；
- 大规模重构、合并、正式文档重写；
- 需要并行 Agent、外部 Agent 委派或与学习分支隔离的任务。

复杂任务才可以按实际风险使用独立 worktree、阶段计划和必要的 superpowers skill；“复杂”不代表必须加载完整 superpowers 流程。简单任务只有在用户主动点名时才调用 `superpowers:*`。

### 7.1.2 架构选型记录

正式架构选型记录放在 `docs/superpowers/architecture-decisions/`，采用“一项重要决定一份文档”，至少写明背景、候选方案、选择标准、最终决定、拒绝原因、正负结果、适用边界和重新评估条件。

当方案满足以下任一条件时，负责设计的 Agent 必须先向用户询问是否记录架构选型；用户已经主动要求记录时不重复询问：

- 决定难以低成本回滚，或会形成长期数据、协议和迁移约束；
- 影响多个阶段、多个 Agent 或公共 Harness/中间件；
- 改变状态所有权、HITL、安全、权限、隐私或副作用边界；
- 引入或替换核心技术栈、外部服务、持久化方式或扩展协议；
- 在两个以上可行方案间做出会影响后续实现方向的明确取舍。

局部命名、可逆重构、单文件实现细节和不影响公共契约的库内选择不触发询问。Agent 应批量提出相关架构问题并给出推荐默认值，避免把一次设计拆成大量确认轮次。架构选型记录解释“为什么这样选”，产品 spec 解释“系统要怎样工作”，implementation plan 解释“按什么步骤落地”，三者不得互相替代。

### 7.2 开发中

- 继续使用测试驱动、逐任务审阅和验证。
- 同步记录关键设计理由、失败尝试、真实缺陷和修正。
- 前端随功能演进，不把新能力长期隐藏在不可操作的后端接口中。
- 对外部 Agent 的产出由 Codex 独立审阅和验收。
- 每个任务只运行受影响的定向测试；全量后端/前端回归每阶段最多两次。
- 前端闭环接通后立即运行一条最小浏览器 happy path，最终只运行一次完整浏览器验收。
- 单个切片默认由一个 Agent 负责到底，避免中途交接重新加载全部上下文。
- 同一 skill 或命令连续两次产生相同失败时停止重试，记录根因并切换诊断路径。
- 工具先用 `rg`、`git diff --stat` 缩小范围，单次输出默认控制在约 4,000 tokens。

### 7.3 开发后

阶段结束时同时更新：

- 产品进度、成熟度和下一阶段；
- 代码地图和人工验证指南；
- 所有权掌握包；
- 理解债务；
- 一个非阻塞的用户所有权练习。

### 7.4 Verification 文档生命周期

每个产品切片维护一份本地验证文档：

```text
docs/verification/<stage>.md
```

该文档是产品验收证据的本地入口，必须随开发过程增量更新，不能等阶段结束后依赖聊天记录或记忆一次性补写。

每个 Task 完成后至少记录：

- 本次实现的行为和主要代码入口；
- 实际执行的自动测试命令与真实结果；
- 已完成和仍待完成的人工验证；
- 开发或验收中发现的问题、修正方式和残余风险。

阶段结束前必须再次刷新：

- 最终完整测试、类型检查和构建结果；
- 浏览器或其他人工验收的逐步操作与预期结果；
- 生成的本地文件、数据库或目录；
- 当前产品成熟度，以及明确属于后续阶段的边界。

阶段结束时必须将增量证据整理为最终用户验证指南，固定使用 `docs/superpowers/templates/stage-verification-template.md` 的五个二级章节：

1. 这次实现了什么；
2. 代码地图；
3. 自动验证；
4. 人工验证；
5. 当前边界。

`progress.md` 是 Task 状态、测试数字、失败尝试和提交记录的开发流水账。最终 verification 不能以 `Task 进度` 或纯 Task 列表为主体，必须让用户能够从零启动、理解和验收完整切片。

Verification 文档必须以最终代码和最新验证输出为准。过期测试数字、已失效路径、旧 UI 文案和不再成立的验证步骤必须在交付前修正。

`docs/verification/` 始终由 Git 忽略，不得暂存或提交。产品分支或 worktree 合并后，负责产品交付的 Codex 会话必须：

1. 将该阶段 verification 文档显式同步到主仓库的同一路径；
2. 验证主仓库目标文件存在且内容为最新版本；
3. 在最终汇报中提供主仓库中的本地文件路径。

Verification 同步和存在性检查完成前，阶段产品功能可以已经合并，但交付收尾不能标记为完成。产品开发会话负责维护和同步 verification；学习会话不得并发修改该文件。

## 8. 所有权掌握包

每个主要切片在本地目录创建：

```text
docs/learning/<stage>/
  overview.md
  architecture.md
  code-walkthrough.md
  failure-journal.md
  interview-questions.md
  exercises.md
  presentation-script.md
```

该目录默认由 `.gitignore` 忽略，只在用户本地保留。正式架构决定仍写入 `docs/superpowers/`。

掌握包必须基于最终代码和真实开发记录，不使用与实现不符的通用教程填充。

七件套的风险档案、必需章节、内容证据和非阻塞练习规则由 `docs/superpowers/templates/stage-learning-pack-template.md` 定义。阶段开始只确定 `foundation`、`stateful`、`integration` 或 `experience` 档案及其风险驱动；实现稳定后生成一次七件套，最终验收后只刷新代码与证据。单个 `README.md` 不能代替七件套；`failure-journal.md` 只记录真实故障，不能为了填充结构虚构问题。

### 8.1 阶段文档质量门禁

阶段关闭前必须运行：

```bash
python3 scripts/check_stage_docs.py \
  --verification docs/verification/<stage>.md \
  --learning docs/learning/<stage>/ \
  --plan docs/superpowers/plans/<current-stage>.md
```

脚本负责确认 verification 的最终结构、可执行命令和人工步骤，learning 七件套的风险档案、结构化深度证据，以及正式计划的浏览器验收勾选状态。计划未完成浏览器验收、learning 档案不匹配门禁或文档证据互相矛盾时，不能将阶段标记为“可人工验证”或“交付完成”。门禁不使用总行数或字数阈值。

脚本通过后，负责交付的 Codex 还必须人工确认：

- 对照上一同档案阶段，状态所有权、真实链路、失败边界和练习证据没有明显退化；
- 代码地图、测试数字和操作步骤来自最终代码与最新输出；
- failure journal 只写真实故障；
- learning 足以支持 Explain、Trace、Review、Debug 或实现练习；
- 产品成熟度与用户掌握度仍分开陈述。

机器门禁负责拦截结构和证据明显缺失，人工门禁负责确认语义真实且没有堆字。每阶段只在最终代码稳定后运行一次完整机器门禁和一次人工抽查；修正时只重跑受影响检查。结果必须写入 verification、`progress.md` 和最终交付汇报。用户是否完成 learning 练习不属于门禁条件。

## 9. 用户所有权练习

每个大阶段生成一个练习，但遵守：

- 不阻塞产品开发、提交、合并或下一阶段；
- 可以在正式功能完成后再做；
- 可以放在独立学习分支或本地练习目录；
- 不要求从零实现完整模块；
- 可以根据用户时间和当前能力降级。

练习形式从高到低包括：

1. 独立实现一个边界清晰的小功能；
2. 根据已有失败测试补实现；
3. 修改或扩展现有行为；
4. 定位并修复注入故障；
5. 完成代码审阅并提出修正；
6. 画流程、写伪代码并解释设计。

未完成练习进入理解债务，不记为产品缺陷。

## 10. 理解债务

每个阶段按三类记录：

```text
已掌握：可以脱离文档解释并回答追问
待掌握：已有材料，但尚未完成讲解验证
待实践：需要通过修改、调试或审阅证明
```

理解债务按目标岗位优先级清偿，而不是平均学习所有模块。例如 Runtime 岗位优先 R1.2，Tool Use 岗位优先 R1.3，HITL 岗位优先 R1.4。

## 11. 并行产品开发与学习分支

当产品轨道领先于所有权轨道时，产品继续向后开发，尚未学习的阶段按顺序进入理解债务队列。不得为了等待用户完成较早阶段的练习而暂停后续产品阶段。

### 11.1 阶段学习基线

- 每个阶段完成时记录对应的产品完成提交或稳定 tag，并写入该阶段 `overview.md`。
- 学习某阶段时，以该阶段的产品完成提交作为代码基线，避免后续业务演进干扰阶段核心概念。
- 每个学习分支必须直接从自己的阶段完成提交创建，不能从前一个学习分支继续派生。
- 未开始的阶段只保留掌握包、基线提交、练习和理解债务状态，不提前创建分支或 worktree。

推荐命名：

```text
learn/r1-2-runtime
learn/r1-3-tool-security
learn/r1-4-hitl
```

### 11.2 单活学习环境

- 同一时间只维护一个活跃学习分支和一个学习目录。
- 主仓库目录固定保持 `main`；产品代码修改始终在独立 worktree 中进行。
- 只有产品开发与用户学习真实并行时，才为活跃学习分支创建独立 worktree。
- 两个会话不得同时操作同一个工作目录、运行数据库或开发端口。
- 学习环境使用独立测试 Workspace 和端口；自动测试优先使用临时目录。
- `docs/learning/` 被 Git 忽略，创建学习 worktree 时由负责 Agent 显式同步对应掌握包，不要求用户手工复制。

### 11.3 学习队列推进

用户完成当前阶段练习并通过所有权验收后：

1. 保留当前学习分支作为历史证据，或在确认没有保留价值后清理；
2. 释放同一个学习 worktree；
3. 从下一阶段的产品完成提交创建新的独立学习分支；
4. 同步下一阶段掌握包并继续学习；
5. 产品轨道不等待上述过程。

学习分支不得形成 `learn/r1-2 -> learn/r1-3 -> learn/r1-4` 的堆叠关系，避免实验代码和未完成改动跨阶段传播。

### 11.4 与当前主线对齐

阶段学习分两步完成：

1. 在阶段完成提交上理解当时的架构、代码链路和设计取舍；
2. 对比当前 `main`，补充相关模块的后续演进、仍然成立的原则和已经替换的实现细节。

基于历史基线完成的练习代码不直接合并到最新主线：

- 纯练习、故障注入和实验性修改只保留为学习证据；
- 已被后续阶段替代的功能不合并；
- 仍有产品价值的改动由 Codex 基于最新 `main` 重新审阅、适配和验证后再进入产品分支。

### 11.5 多会话文件所有权

- 产品开发会话负责正式 spec、plan、`task_plan.md`、`findings.md` 和 `progress.md`。
- 学习会话只修改活跃学习分支中的练习代码、测试和本地 `docs/learning/<stage>/` 材料。
- 学习验收完成后，由产品开发会话或 Codex 统一更新理解债务状态，避免两个会话并发修改共享规划文件。

## 12. 所有权验收

所有权验收包含四种证据：

- Explain：能解释问题、架构和取舍；
- Trace：能沿代码追踪一次真实请求；
- Change：能完成一个有边界的改动；
- Debug：能定位一个真实或注入的故障。

这些证据用于判断用户掌握度，不影响产品阶段完成状态。

## 13. 委派规则

- Codex：架构、复杂跨层实现、关键状态机、安全边界、审阅和验收。
- Claude：普通、边界清晰、上下文可最小化的实现任务。
- 用户：产品取舍、最终边界确认和非阻塞所有权练习。

不得为了节省 Token 把高风险任务交给缺少必要上下文的外部 Agent。不得把整个私有工作区无差别发送给外部 Agent，只提供任务所需的最小上下文。

## 14. 文档与 Git 规则

- `docs/my_idea.md` 保持只读且不提交。
- 正式设计和实施计划只提交 `docs/superpowers/` 下的文档。
- `task_plan.md`、`findings.md`、`progress.md` 继续纳入 Git。
- `docs/verification/` 和 `docs/learning/` 为本地材料，合并分支时需要显式同步到主仓库。
- `docs/verification/<stage>.md` 按第 7.4 节增量维护；同步和存在性检查是产品交付收尾门槛。
- 每个阶段完成时，代码状态、产品成熟度和掌握状态必须分别描述。

## 15. 成功标准

该工作流建立后：

1. 新 Codex 会话和 Claude Code 会话能够从仓库恢复相同准则。
2. 上下文压缩后可以通过文件继续开发，而不依赖旧聊天全文。
3. 用户学习速度不会阻塞产品路线。
4. 每个阶段结束时都有可延后消费的掌握材料和练习。
5. 面试准备时可以按岗位快速定位相关架构、故障和代码链路。
6. 项目对外介绍能够诚实区分 Agent 协作实现与用户已经验证的个人掌握能力。

## 16. 执行预算

- 根启动入口合计不超过 400 行。
- 单次工具返回默认不超过约 4,000 tokens。
- 单阶段全量后端回归不超过两次，前端回归与 build 不超过两次。
- 完整浏览器验收一次；修复后只重跑受影响场景。
- 默认零中途 Agent 交接、零 subagent。
- 相同失败最多重复一次；第二次相同失败转根因诊断。
- 每个纵向任务的 handoff 摘要不超过 10 行。
