# Agent 质量中心与面试复盘评估设计

- 日期：2026-08-04
- 状态：Approved for implementation
- 适用范围：Agent 注册中心、质量评估服务、面试复盘 Agent、质量中心前端
- 基线设计：`2026-07-31-agent-evaluation-v2-design.md`

## 1. 背景与现有问题

当前质量页面已经具备历史结果复检、确定性规则、AI Judge、人工反馈、回归案例和趋势等能力，但产品入口仍以技术实现组织，导致用户难以回答三个最基本的问题：

1. 这里是在检查什么；
2. 哪些 Agent 可以检查；
3. 发现问题后下一步该做什么。

同时，Agent 注册契约存在能力声明不完整的问题：`interview.retrospective` 声明了 `manual_judge`，却没有绑定 `eval_pack_id`。页面可能展示质量检查入口，评估 API 最终才返回“不支持质量评估”。这属于控制面声明和运行时能力不一致，不能继续由页面猜测或在调用后兜底。

## 2. 目标与非目标

### 2.1 目标

- 让质量中心默认以业务任务而不是评估术语组织信息；
- 建立“选择运行 → 检查结果 → 人工确认”的主流程；
- 将回归实验、质量趋势从日常检查流程中拆出，但保留现有能力；
- 让所有质量入口严格服从 Agent 注册中心中的评估能力声明；
- 为面试复盘补齐可执行、可解释的 v2 Eval Pack；
- 保持历史 Execution、Trace、回归案例与路由兼容；
- 在桌面和窄屏下都保持清晰的信息层级和可操作性。

### 2.2 非目标

- 本轮不把面试复盘整理、分析、讨论和历史检索拆成四个 Agent 定义；
- 不新增跨 Agent 综合百分制；
- 不把 AI Judge 的建议自动写回业务结果；
- 不将当前告警型质量规则升级为发布阻断门禁；
- 不修改既有 Agent 的业务执行流程。

## 3. 关键设计决策

### 3.1 面试复盘采用一个 Eval Pack

新增 `interview-retrospective.v2`，绑定到控制面 Agent `interview.retrospective`。整理、逐题分析、讨论与历史检索仍属于同一个用户能力域，共用一套身份、来源和状态边界。

评估时根据 Execution 的 `graph_id`、运行模式和业务结果投影决定维度适用性：

- 代码能判定时，由 Outcome Adapter 标记 `applicable` 或 `not_applicable`；
- 证据缺失但理论上应评价时，标记 `insufficient_evidence`；
- Judge 不得把不适用维度按满分计入结果。

选择一个 Pack 而不是多个 Pack 的原因：

- 不改变现有 Agent 注册和运行中心聚合模型；
- 历史别名与 Trace 无需迁移；
- 同一复盘会话的整理、分析和讨论可以共享领域边界；
- 后续若某个子模式形成独立生命周期，再通过新的 Agent Definition 拆分，而不是提前制造控制面碎片。

### 3.2 评估能力由注册中心单点声明

Agent Definition 必须满足以下不变量：

```text
manual_judge in capabilities  <=>  eval_pack_id is not null
```

注册阶段校验 Eval Pack 是否存在。任何页面、API 或运行中心不得根据 `graph_id`、名称、历史经验推测支持状态。

对历史快照继续遵循冻结语义：旧 Execution 没有 `eval_pack_id` 时，不静默套用新 Pack；页面显示“该历史运行创建时尚未启用质量检查”，允许用户通过一次明确的新版本复检迁移流程处理，不能篡改原快照。

### 3.3 页面采用日常检查与实验分析分层

质量中心设置三个同级入口：

1. **质量检查**：默认入口，面向日常结果复核；
2. **回归实验**：比较基线与候选版本，管理真实案例；
3. **质量趋势**：观察 Agent、版本和时间维度的长期变化。

高级技术细节不再与日常操作并列堆叠。规则证据、Judge 原始结果、Trace、Token 和运行环境进入展开区或高级详情。

## 4. 面试复盘 Eval Pack

### 4.1 结果投影

Outcome Adapter 从复盘领域状态、Receipt、用户确认和 Execution 快照构建：

```text
identity
  workspaceId / retrospectiveId / executionId / graphId / mode

input
  sourceDocumentVersion / selectedQuestionId / query / scope

result
  transcriptDraft / confirmedTranscript
  extractedQuestions / confirmedQuestions
  questionAnalyses / discussionMessages
  historyMatches / generatedReport

provenance
  sourceRange / sourceHash / questionEvidence
  inferredQuestion / userConfirmation

userDecision
  transcriptDecisions / inferredQuestionDecisions
  acceptedEdits / rejectedEdits

runtime
  model / prompt / tool / schema / context / code versions
  latency / token / retry / cancellation summary
```

Trace 只用于解释调用过程；领域表、Receipt 和用户确认是最终结果事实来源。

### 4.2 维度

| 维度 | 适用模式 | 判定方式 | 核心问题 |
|---|---|---|---|
| 转写忠实与修订边界 | 整理 | Hybrid | 纠错是否保持事实、数字、职责和术语边界，是否能追溯原文？ |
| 不确定项与人工确认 | 整理 | Rule | 低置信度术语、说话人和推断问题是否进入确认流程？ |
| 说话人与问题恢复 | 整理 | Judge | 主要说话人是否合理；推断问题是否保守且明确标记？ |
| 问题提取完整性 | 分析 | Hybrid | 已确认文本中的明确问题是否被提取，证据是否可定位？ |
| 推断问题边界 | 分析 | Rule | 推断题是否与明确题区分，是否等待用户确认？ |
| 分析依据与忠实度 | 分析 | Hybrid | 结论是否基于回答和证据，是否虚构技术细节或抬高职责？ |
| 改进建议可行动性 | 分析 | Judge | 建议是否具体、与问题相关且能指导下一次回答？ |
| 讨论直接性与上下文 | 讨论 | Judge | 是否直接回答当前追问，并正确使用选中题目和工具结果？ |
| 讨论写入边界 | 讨论 | Rule | 讨论是否只生成建议，未经确认不改正式复盘结果？ |
| 历史检索来源覆盖 | 历史检索 | Hybrid | 命中是否来自允许的已确认数据，场次与题目引用是否完整？ |
| 总结报告证据一致性 | 历史检索 | Judge | 总结是否覆盖检索结果且没有增加未检索到的经历？ |
| 生命周期与幂等 | 全部 | Rule | 停止、重试、恢复、迟到结果和重复写入是否符合状态机？ |

### 4.3 聚合规则

- 只聚合 `applicable` 的维度；
- `insufficient_evidence` 单列为“证据不足”，不转换为低分；
- 任意确定性高风险规则失败时，结果至少进入“需要关注”；
- AI Judge 只给出质量建议，不能覆盖确定性规则或人工确认；
- 用户反馈保存到 Evaluation Rating，不直接修改业务数据。

## 5. 质量检查页面

### 5.1 顶层信息架构

页面标题改为“Agent 质量中心”，副标题明确：

> 检查 Agent 已生成的业务结果，确认问题，并把真实案例保存为回归样本。

顶层导航：

```text
质量检查 | 回归实验 | 质量趋势
```

不再使用“运行中心 / 运行质量 / 高级评估”多层切换描述同一页面。

### 5.2 质量检查主流程

#### 第一步：选择一次运行

- 默认展示“需要检查”的运行；
- 支持按 Agent、时间和状态筛选；
- 每项明确显示 Agent 名称、业务任务、更新时间、是否支持检查；
- 不支持的运行保留可见，但按钮改为“暂不支持”，并展示具体原因；
- 已检查、待确认、检查失败使用文字和图标共同表达，不能只依赖颜色。

#### 第二步：查看检查结果

首屏只展示：

- 总结：稳定 / 需要关注 / 严重问题 / 证据不足；
- 最重要的 1～3 个问题；
- 确定性规则与 AI 建议的来源标签；
- 影响范围和推荐动作。

完整维度、证据、技术指标和 Judge 原始结果按需展开。

#### 第三步：人工确认

- “确认无问题”；
- “确认有问题”；
- “暂不判断”；
- 可选保存为回归案例；
- 人工判断与 AI 判断并列保存，不能互相覆盖。

页面每个状态只保留一个主按钮，其他操作降级为次要按钮或更多菜单。

### 5.3 回归实验

- 基线版本与候选版本明确成对展示；
- 先选择案例集，再运行比较；
- 显示新增问题、已修复问题、保持稳定和证据不足；
- 保留现有 Regression Case 能力，避免在日常检查页面直接暴露全部实验设置。

### 5.4 质量趋势

- 默认按 Agent 显示“稳定、关注、风险、证据不足”的数量趋势；
- 支持按版本和时间范围筛选；
- 趋势图提供同内容的可访问数据表；
- 没有数据时说明需要先完成质量检查，不能展示空图框。

## 6. 页面布局与响应式

### 6.1 桌面端

- 页面最大内容宽度服从现有工作台规范，不使用超宽长文本；
- 运行列表和检查内容采用可调整的主从布局，详情区优先获得阅读宽度；
- 右侧辅助栏只放人工判断与来源概览，不堆叠全部技术信息；
- 长列表独立滚动，但避免三列同时出现竞争滚动条。

### 6.2 中小屏

- 低于 1024px 改为列表 → 详情的两级导航；
- 低于 768px 顶层入口可横向滚动但不截断文字；
- 所有可点击区域至少 44×44px；
- 不允许整页横向滚动；
- 返回详情时恢复筛选和列表滚动位置。

### 6.3 视觉原则

- 沿用现有工作台颜色、字体和组件 Token，不引入新的紫粉色视觉体系；
- 通过留白、字号、标签和分组建立层级，避免大面积装饰色；
- 仅对状态变化使用 150～250ms 的轻量过渡，并支持 reduced motion；
- 技术术语使用中文主标签，英文标识仅作为辅助信息。

## 7. 错误与空状态

- 不支持评估：说明是 Agent 未注册、历史快照未启用或 Pack 不可用；
- 证据不足：列出缺少的证据和可采取的补救动作；
- 检查失败：保留原业务结果，提供重试和打开运行详情；
- 无历史结果：引导用户先选择一个已完成且支持评估的运行；
- 趋势无数据：引导完成至少一次质量检查；
- API 不再把所有不支持情况折叠成同一条通用错误。

## 8. 兼容与迁移

- 新的 Agent Definition 快照开始绑定 `interview-retrospective.v2`；
- 既有快照保持冻结，不进行后台批量改写；
- 现有质量报告、Rating、Regression Case 和 Trace 数据结构保持兼容；
- 旧的 `view=overview/tools` 路由参数在一个迁移周期内映射到新入口；
- 深链接仍可直接打开指定 Evaluation Report；
- 前端所有支持状态从后端能力契约读取。

## 9. 验收标准

### 9.1 契约与后端

- 声明 `manual_judge` 但未绑定有效 Pack 的 Agent 无法注册；
- `interview.retrospective` 新 Execution 冻结正确的 Pack ID；
- 整理、分析、讨论、历史检索只评价适用维度；
- 历史不支持快照返回可解释原因，不被静默升级；
- Judge 失败不修改复盘业务结果。

### 9.2 前端

- 首次进入页面可以在 10 秒内理解页面用途和下一步；
- 默认只出现“选择运行 → 查看结果 → 人工确认”的主路径；
- 不支持的运行不会出现可提交的“开始检查”按钮；
- 回归和趋势不再挤占日常检查首屏；
- 1440、1024、768、390px 无整页横向滚动；
- 键盘可完成选择、展开、确认和返回；
- 状态不只依赖颜色表达。

### 9.3 回归

- 现有支持质量评估的 Agent 继续可用；
- 现有历史报告、反馈、案例和趋势可以读取；
- Agent 运行中心的质量入口与注册中心能力保持一致；
- 未启用质量评估的系统 Agent 不显示误导性主操作。
